# 知识图谱与 GraphRAG

> 向量检索靠**向量数据库**，知识图谱靠**图数据库**。前者擅长语义匹配，后者擅长关系推理。

---

## 一、知识图谱是什么

把信息组织成**实体-关系-实体**的网络结构，而不是扁平的文档列表。

```
传统知识库（扁平文档）：
  文档1: "周杰伦演唱会8月15日北京鸟巢"
  文档2: "退票政策：演出前48小时可退"
  文档3: "鸟巢可容纳8万人"

知识图谱（💥关系网络💥）：
  周杰伦演唱会 ──演出时间──→ 8月15日
  周杰伦演唱会 ──演出地点──→ 鸟巢
  周杰伦演唱会 ──退票政策──→ 演出前48小时可退
  鸟巢 ──容纳人数──→ 8万人
  鸟巢 ──所在城市──→ 北京
```

---

## 二、核心概念

| 概念 | 说明 | 示例 |
|------|------|------|
| **实体（Entity）** | 具体事物 | 周杰伦、鸟巢、北京 |
| **关系（Relation）** | 实体间的联系 | 演出地点、所在城市 |
| **三元组** | 知识图谱的基本单元 | (周杰伦, 演出地点, 鸟巢) |
| **属性（Property）** | 实体的特征 | 鸟巢.容纳人数 = 8万 |

## 三、图数据库

### 代表产品

| 图数据库 | 特点 | 适用场景 |
|---------|------|---------|
| **💥Neo4j💥** | 最流行，生态完善，Cypher 查询语言 | 企业级首选 |
| **NebulaGraph** | 国产，分布式，高性能 | 大规模数据 |
| **JanusGraph** | 开源，兼容多种存储后端 | 需要灵活存储 |
| **ArangoDB** | 多模型（图+文档+KV） | 混合场景 |

### 查询语言：Cypher

```cypher
-- 查找"鸟巢"举办的所有演出
MATCH (venue {name: "鸟巢"})-[:举办演出]->(show)
RETURN show.name

-- 查找"退票手续费"的具体规定
MATCH (policy {name: "退票政策"})-[:包含]->(rule {name: "退票手续费"})
RETURN rule.content

-- 查找两跳关系：北京 → 场馆 → 演出
MATCH (city {name: "北京"})-[:包含场馆]->(venue)-[:举办演出]->(show)
RETURN show.name, venue.name
```

## 四、三种检索方式互补（关键词   vs   向量   vs   知识图谱）

### 向量检索的本质与边界

**本质**：向量检索本质上是一个❇️**相似度排序系统**，做的是文本匹配，不是在做关系推理。

```
擅长：查概念、查说明、查流程、查规则。答案通常就在某个 chunk 里。
局限：一旦问题涉及多个实体之间的关系，或者需要多跳查询，向量检索就会开始吃力。
```

**向量检索适合做入口定位，但不适合承担完整的多跳关系推理。**

**选择标准**：
```
答案在文档里 → 向量检索更合适
答案在关系链里 → 考虑图数据库
如果问题没有关系链可遍历，向量检索反而更合适
```

### 对比

| 维度 | 关键词检索（BM25） | 向量检索 | 知识图谱 |
|------|------------------|---------|---------|
| 存什么 | 词频统计 | 向量（浮点数数组） | 节点 + 边 |
| 查询方式 | 关键词匹配 | 相似度搜索 | 图遍历 |
| 擅长 | 💥**精确**匹配专有名词 | 💥**语义**理解、同义词 | 实体💥**关系**、跨文档关联 |
| 不擅长 | 同义词、语义理解 | 精确关键词、关系推理 | 模糊语义理解 |
| 查询语言 | BM25Okapi | `similarity_search()` | Cypher / Gremlin |
| 代表产品 | rank_bm25 | ChromaDB、Milvus | Neo4j、NebulaGraph |

**图数据库不是用来替代向量检索的，它真正补上的是关系链推理能力。**

### 三者互补

```
用户问："鸟巢附近的演出"

BM25：找到包含"鸟巢"的文档     		✅ 精确匹配
向量：找到语义相关的"体育馆演出" 	   	 ✅ 语义理解
图谱：鸟巢 → 北京 → 附近场馆 → 演出 	  ✅ 关系推理
```

**企业级 RAG 越来越倾向于三种方式混合使用，不是选一个，而是组合用。**

```
                 用户问题
                    ↓
┌─────────────────────────────────────┐
│  BM25 检索  │   向量检索   │  图谱查询  │
│  关键词匹配  │   语义相似   │  关系遍历  │
└──────┬──────┴──────┬────┴──────┬────┘
       └─────────────┴───────────┘
                     ↓
            RRF 融合排序 → Top-K
```

**适用场景**：法律法规（关键词精确 + 语义理解 + 条文引用）、医疗问答（症状匹配 + 语义理解 + 疾病-药物关系）、客服系统（产品名精确 + 模糊问题理解 + 产品-功能关系）。

## 五、GraphRAG：知识图谱 + RAG

```
    用户问题
       ↓
┌─────────────┐
│   向量检索   │ → 语义相关的文档片段
└──────┬──────┘
       │
┌──────┴──────┐
│ 知识图谱查询 │ → 实体关系、跨文档关联
└──────┬──────┘
       │
       ▼
   合并结果 → LLM 生成回答
```

**GraphRAG = 向量检索（找语义相关内容）+ 知识图谱（找关系关联内容）**

### 三步组合方式

```
第一步：入口定位
  向量检索先找到相关文档，并识别关键实体。
  → 向量检索负责找到"入口"

第二步：关系遍历
  把关键实体映射到图数据库节点，再沿着关系边继续查。
  → 图数据库负责沿着关系"走下去"

第三步：结果生成
  把文本证据和关系路径一起交给大模型生成回答。
  → 文本证据 + 关系路径 → LLM 生成
```

**一句话总结**：向量检索负责找到入口，图数据库负责沿着关系走下去。

**面试话术**：
> "GraphRAG 的组合方式是三步：先用向量检索定位文本和关键实体，再用图数据库做关系遍历，最后把文本证据和关系路径交给大模型生成回答。向量检索负责找到入口，图数据库负责沿着关系走下去。两者不是替代关系，而是互补关系。"

## 六、知识图谱能做什么向量检索做不了的

```
用户问: "北京有哪些演唱会？"

向量检索：找到包含"北京"和"演唱会"的文档片段
  → 可能漏掉只写了场馆没写城市的

知识图谱：
  北京 ──包含场馆──→ 鸟巢
  鸟巢 ──举办演出──→ 周杰伦演唱会
  鸟巢 ──举办演出──→ 林俊杰演唱会
  → 沿关系链查找，不遗漏
```

## 七、💥构建知识图谱的流程

```
原始文档: "周杰伦演唱会8月15日在北京鸟巢举办"
  │
  │ 实体识别（NER）
  ↓
实体: 周杰伦演唱会、8月15日、北京、鸟巢
  │
  │ 关系抽取
  ↓
三元组: (周杰伦演唱会, 演出时间, 8月15日)
        (周杰伦演唱会, 演出地点, 鸟巢)
        (鸟巢, 所在城市, 北京)
  │
  │ 写入图数据库
  ↓
Neo4j 存储节点和边
```

**构建方式**：
- **自动抽取**：用 LLM 从文档中提取实体和关系
- **半自动**：LLM 抽取 + 人工校验
- **手动构建**：适合小规模、高精度场景

## 八、💥知识图谱的检索流程

```
用户问: "鸟巢附近有什么演出"

第一步：💥实体识别（NER / LLM）
  提取实体: "鸟巢"
  识别意图: 查询演出

第二步：💥图查询（Cypher）
  MATCH (venue {name: "鸟巢"})-[:举办演出]->(show)
  RETURN show.name, show.time

第三步：💥沿关系链遍历
  鸟巢 ──举办演出──→ 周杰伦演唱会（8月15日）
  鸟巢 ──举办演出──→ 林俊杰演唱会（9月20日）

第四步：返回结果
  "鸟巢近期有周杰伦演唱会（8月15日）和林俊杰演唱会（9月20日）"
```

**多跳查询**（沿关系链逐层查找）：

```
用户问: "北京朝阳区有什么演出"

第一跳：北京 → 包含区域 → 朝阳区
第二跳：朝阳区 → 包含场馆 → 鸟巢、工体...
第三跳：场馆 → 举办演出 → 具体演出列表
```

向量检索做不到这种多跳推理，图谱可以沿着关系链逐层查找。

**GraphRAG 检索流程**（图谱 + 向量结合）：

```
    用户问题
       ↓
    实体识别（NER / LLM）→ 提取实体："鸟巢"、"北京"
       ↓
┌──────────────┐
│   图谱查询    │  沿关系链遍历
│   (Cypher)   │  鸟巢 → 演出 → 时间/价格
└──────┬───────┘
       │
┌──────┴───────┐
│   向量检索    │  语义相关的文档片段
│ (Embedding)  │  "鸟巢场馆介绍"、"演出规则"
└──────┬───────┘
       ↓
  合并结果 → LLM 生成回答
```

## 九、什么场景适合知识图谱

| 场景 | 为什么需要知识图谱 |
|------|------------------|
| **法律法规** | 条文之间有引用关系（"依据第 xx 条"） |
| **医疗知识** | 症状→疾病→药物→副作用有复杂关联 |
| **金融风控** | 企业→股东→关联公司→风险传导 |
| **客服问答** | 产品→功能→故障→解决方案有依赖链 |
| **企业关系分析** | 投融资、股权穿透、人员任职、供应链上下游、竞争合作关系 |
| **代码知识库** | 函数调用、模块依赖、接口上下游、服务调用链 |
| **供应链溯源** | 原材料、供应商、批次、成品、渠道，本身就是层级关系 |

**共同特征：关系密集、实体复杂、需要多跳推理。**

**选择标准**：当业务问题涉及多个实体之间的关联推理，尤其需要沿着实体关系做多跳查询时，就可以考虑引入图数据库来增强向量检索。

## 十、面试高频问题

| 问题 | 回答要点 |
|------|---------|
| 知识图谱是什么？ | 把信息组织成实体-关系-实体的网络结构 |
| 知识图谱和向量检索的区别？ | 向量擅长语义匹配，图谱擅长关系推理，两者互补 |
| 什么场景需要知识图谱？ | 有复杂关联关系的场景：法规、医疗、金融、客服 |
| GraphRAG 是什么？ | 向量检索 + 知识图谱查询，两者结合覆盖更多场景 |
| 知识图谱怎么构建？ | 实体识别（NER）→ 关系抽取 → 三元组 → 写入图数据库 |
| 图数据库用什么？ | Neo4j（最流行）、NebulaGraph（国产分布式） |
| 向量检索和图数据库怎么组合？ | 三步：向量检索定位入口 → 图数据库关系遍历 → 合并结果生成回答 |
| 什么时候该用图数据库？ | 问题涉及多实体关联推理、需要多跳查询时；答案在关系链里而非文档里 |

## 十一、面试话术

> "**知识图谱把信息组织成实体-关系-实体的网络结构，适合有复杂关联关系的场景。和向量检索互补：向量检索擅长语义匹配，知识图谱擅长关系推理。GraphRAG 把两者结合，检索时同时查向量库和图谱，覆盖更多场景。当前项目文档是独立 Q&A 格式，没有复杂关联，用向量检索够用。**"
