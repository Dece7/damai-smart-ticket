# RAG 知识库文档更新

> RAG 知识库更新的核心，不是"怎么更新一个 chunk"，而是"怎么可靠地感知变化、删干净旧数据、再稳定写入新数据"。

---

## 一、面试常见误区

**面试提问**：RAG 知识库上线后，文档更新怎么办？

❌**错误回答**：
> "找到变动的 chunk，重新 embedding 一下就行。"

**为什么错**：
> 这句话听起来精细，但生产环境很危险。RAG 的文档不是数据库一行记录，文档入库前要经历：切分 chunk → embedding → 写入向量库。任意一段文字变化，都可能影响后续切分。chunk 级局部更新，看起来精细，实际最容易留下新旧内容混杂。

**面试官真正想听的**：
> 你有没有处理过生产级 RAG 的数据一致性问题。

---



## 二、核心问题：💥文档一变，chunk 边界会漂移

```
原文档：
  "## 退票政策\n退票需要在演出前48小时申请，票款3个工作日退回。"

切出的 chunk：
  chunk_001: "退票需要在演出前48小时申请，票款3个工作日退回。"

文档修改后：
  "## 退票政策\n退票需要在演出前48小时申请，票款7个工作日退回。扣除10%手续费。"

如果只更新 chunk_001 里的"3个工作日"→"7个工作日"：
  ❌ 新增的"扣除10%手续费"没有对应的 chunk
  ❌ chunk 边界可能因为内容长度变化而漂移
  ❌ 新旧内容混杂，检索结果混乱
```

**本质**：chunk 不是独立的记录，它是文档切分的产物。文档变了，chunk 的边界、数量、内容都可能变。局部更新 chunk 无法保证一致性。

---



## 三、生产方案：💥先删后增

```
检测文档变化 → 删除旧 chunk → 重新切割 → 重新 embedding → 写入向量库
```

**为什么不是"越精细越好"**：

> 工程里更重要的是可控。旧 chunk 没删干净，新内容又写进来，检索就会混乱。

**听起来粗暴，但更可靠**：
> 只要确认某篇文档改了，就把这篇文档对应的旧向量全部清掉，再写入新版本。

**修改文档的默认策略**：不要试图局部对齐 chunk，先按文档维度删除，再重建。

**面试话术**：
> "文档修改的策略是先删后增。检测到文档变化后，**先删除这篇文档的所有旧 chunk，再重新切割、重新 embedding、重新写入向量库**。听起来粗暴，但比局部更新更可靠——旧 chunk 没删干净，新内容又写进来，检索就会混乱。"

## 四、怎么知道文档变了：content_hash

**第一次入库时记录三类信息**：

| 信息 | 作用 | 示例 |
|------|------|------|
| `document_id` | 文档唯一身份，后续增删改都靠它定位 | `doc_0123` |
| `content_hash` | 内容指纹，用来判断文档是否变化 | `a1b2c3d4e5f6` |
| `chunk_ids` | 这篇文档切出来的所有 chunk 关系 | `["chunk_001", "chunk_002"]` |

**下一次扫描时**：

```
重算 hash → 对比旧 hash → 没变跳过 → 变了重建
```

```python
import hashlib

def compute_hash(content: str) -> str:
    return hashlib.md5(content.encode()).hexdigest()

# 入库时记录
doc_record = {
    "document_id": "doc_0123",
    "content_hash": compute_hash(doc_content),
    "chunk_ids": ["chunk_001", "chunk_002", "chunk_003"]
}

# 扫描时对比
new_hash = compute_hash(new_content)
if new_hash == old_hash:
    skip()  # 内容没变，跳过
else:
    rebuild()  # 内容变了，先删后增
```

**hash 的特点**：
- 计算很快，O(n) 复杂度
- 文档只改一个标点，hash 也会变化
- 大规模场景可先用 `last_modified` 粗筛，再算 hash

```
hash 负责精确判断内容变化
last_modified 负责降低扫描成本，先初筛
```

**面试话术**：
> "用 **❇️content_hash** 判断文档是否变化。入库时记录文档的 hash 值，扫描时重算 hash 对比，没变跳过，变了重建。大规模场景先用 last_modified 粗筛，再算 hash 精确判断。"

## 五、一开始就设计好：文档 ID 与 chunk 的关联

**方案一：chunk ID 带文档 ID**

```
chunk_id: product_manual_chunk_001
          product_manual_chunk_002
          product_manual_chunk_003

删除时按前缀定位：DELETE WHERE chunk_id LIKE "product_manual_chunk_%"
```

**方案二：metadata 存 source_doc_id**

```python
chunk.metadata = {
    "source_doc_id": "doc_0123",
    "source": "product_manual.md",
    "h1": "退票政策",
    "h2": "退票流程"
}

# 向量库支持 metadata 过滤时，按 source_doc_id 批量删除
vectorstore.delete(filter={"source_doc_id": "doc_0123"})
```

**关键原则**：

> 这个能力千万不要上线后再补。如果不知道 chunk 来自哪篇文档，就没法可靠删除旧向量，后续每次更新都会变成清理事故。

**金句**：
> 向量库里的每个 chunk，都必须能反查到它来自哪篇 document。

**面试话术**：
> "一开始就设计好文档 ID 和 chunk 的关联。有两种方案：chunk ID 带文档 ID 前缀，或者 metadata 存 source_doc_id。这个能力千万不要上线后再补，如果不知道 chunk 来自哪篇文档，就没法可靠删除旧向量。"

## 六、文档变化怎么触发：💥轮询 vs 事件驱动

| 方式 | 原理 | 适用场景 | 优点 | 缺点 |
|------|------|---------|------|------|
| **❇️定时轮询** | 每天凌晨/每小时扫描数据源 | 内部知识库、低频 FAQ、产品文档 | 实现简单 | 有延迟 |
| **❇️事件驱动** | 数据源变化后主动发事件（Webhook/Kafka） | 客服知识库、新闻、政策更新 | 实时性高 | 实现复杂 |

```
低频更新用轮询，秒级生效用事件驱动
规模变大后用消息队列解耦
```

**面试话术**：
> "文档变化触发有两种方式：**定时轮询**适合低频更新的内部知识库，实现简单但有延迟；**事件驱动**适合需要秒级生效的场景，通过 Webhook 或 Kafka 通知更新服务。低频用轮询，实时用事件驱动。"

## 七、文档删除：一定要清理僵尸 chunk

**常见错误**：

```
❌ 只删原文档，不删向量库
  → 原文档删了，但向量库里旧 chunk 还在
  → 用户一问，系统仍然可能把旧 chunk 检索出来
  → "僵尸向量"残留
```

**正确删除流程**：

```
定位 document_id → 查询关联 chunk → 批量删除向量 → 删除元数据关系
```

```python
def delete_document(document_id: str):
    # 1. 查询关联的 chunk
    chunk_ids = get_chunks_by_doc_id(document_id)

    # 2. 批量删除向量
    vectorstore.delete(ids=chunk_ids)

    # 3. 删除元数据关系
    delete_doc_record(document_id)
```

**金句**：
> 删除最重要的是删干净，不让旧内容继续参与检索。

## 八、RAG 更新只处理三类变化

| 变化类型 | 处理方式 | 说明 |
|---------|---------|------|
| **新增** | 正常入库 | 切割 → embedding → 写入向量库，记录 document_id、hash、chunk 关系 |
| **修改** | 先删后增 | 删除旧 chunk → 重新切割 → 重新 embedding → 写入新 chunk |
| **删除** | 彻底清理 | 根据 document_id 清理所有关联 chunk，避免僵尸向量残留 |

```
新增走正常入库
修改走先删后增
删除走彻底清理
```

**面试话术**：
> "RAG 更新只处理三类变化：新增走正常入库，修改走先删后增，删除走彻底清理。修改是最容易踩坑的，不要只更新局部 chunk，要先删旧 chunk 再重建。"

## 九、全量重建：不是常规方案，而是最后手段

| 维度 | 说明 |
|------|------|
| **优点** | 逻辑简单，不用担心漏删，不用维护复杂的增量状态 |
| **缺点** | 成本高、时间长，重建过程中可能影响线上服务 |

**什么时候适合全量重建**：

| 场景 | 原因 |
|------|------|
| 知识库很小（几十篇文档） | 重建一次只要几分钟，成本可接受 |
| 换 embedding 模型 | 新旧向量不兼容，只能全量重建 |
| chunking 策略变了 | 切分方式变了，旧 chunk 全部失效 |
| 重大调整 | 版本升级、架构迁移等 |

**面试话术**：
> "全量重建是最后手段，不是常规方案。常规生产优先走增量更新。只有在换 embedding 模型、切分策略变化、或知识库很小时才考虑全量重建。"

## 十、高风险场景：版本灰度

**适用场景**：金融问答、医疗问答、企业合规知识库等不能轻易把旧内容直接删掉的场景。

```
旧库 version=old
  → 新库入库 version=new
  → 测试问题验证质量是否下降
  → 切换检索条件 old 转为 new
  → 异常回滚 new 转为 old
```

**灰度更新的思路类似蓝绿部署**：
- 可验证：新版本先用测试问题验证质量
- 可切换：验证通过后切换检索条件
- 可回滚：出问题可以立刻回滚到旧版本

**面试话术**：
> "高风险场景做版本灰度。新版本入库后先用测试问题验证质量，验证通过再切换检索条件，出问题可以立刻回滚。思路类似蓝绿部署：可验证、可切换、可回滚。"

## 十一、面试回答总结

```
1. 不能简单做 chunk 级局部更新，文档变化会导致 chunk 边界和数量变化
2. 维护 document_id、content_hash、chunk 关系，能定位、能判断、能删除
3. 检测到修改后，先删旧 chunk，再重新切割、embedding、入库
4. 删除文档时必须清理所有相关 chunk，避免旧内容残留
5. 低频用定时轮询，实时用 Webhook / Kafka 等事件驱动
6. 保留 old / new 版本，先验证，再切换，必要时回滚
```

**一句话总结**：
> "RAG 知识库更新的核心，不是'怎么更新一个 chunk'，而是'怎么可靠地感知变化、删干净旧数据、再稳定写入新数据'。"

## 十二、本项目文档更新现状

| 维度 | 状态 | 说明 |
|------|------|------|
| 文档变化检测 | ❌ 未做 | 没有 hash 对比，没有扫描机制 |
| chunk 与文档关联 | ⚠️ 部分 | metadata 有 source 字段，但没有 document_id |
| 增量更新 | ❌ 未做 | 当前是全量重建 |
| 文档删除清理 | ❌ 未做 | 没有删除流程 |
| 版本灰度 | ❌ 未做 | 没有版本管理 |

**为什么没做**：当前是 15 个静态文档，全量重建 30 秒，增量更新的开发成本比它省下的时间还贵。

**面试话术**：
> "**当前项目是 15 个静态文档，用全量重建够用。但架构上是支持扩展的——chunk 的 metadata 可以加 document_id 和 content_hash，向量库支持 metadata 过滤删除。生产环境我会做增量更新：入库时记录 hash，扫描时对比变化，修改走先删后增，删除走彻底清理。**"
