# 项目优化记录

## 1. P0 - Markdown 标题感知切分 + 标题注入（2026-06-14）

**问题**：原方案用 `RecursiveCharacterTextSplitter` 按 500 字符盲切，不感知 Markdown 标题结构，Q&A 知识点容易被截断。

**改动**：
- 引入 `MarkdownHeaderTextSplitter`，按 `#/##/###` 标题层级切分
- 将标题信息注入 chunk 内容（如 `节目取消和退票 > 退票政策\n正文...`），增强 embedding 和 BM25 检索语义
- 对超大块做二次切分（chunk_size=800, overlap=150）

**效果**：15 个文档 → 130 个 parent / 131 个 child 分块，6/6 测试查询全部命中正确文档。

## 2. 知识库补充 - 无障碍服务关键词（2026-06-14）

**问题**：查询"残疾人有什么服务"未能命中"无障碍服务"文档，因文档用词是"残障人士"，BM25 字面匹配失败。

**改动**：在 `无障碍服务-相关问题与回答.md` 中补充"残疾人"关键词。

**效果**：修复后 Top-1 正确命中无障碍服务文档。

## 3. P2 - Parent-Child 分块（2026-06-14）

**问题**：单层分块存在"检索精准 vs 上下文完整"的矛盾——小块检索准但信息少，大块信息全但检索不准。

**改动**：
- 实现 `split_documents_with_parents()`：按标题切出 parent（大块），再切出 child（小块，chunk_size=400）
- child 用于 embedding + BM25 检索，命中后映射回 parent 返回给 LLM
- parent chunks 持久化到 `data/parent_chunks.pkl`
- 向后兼容：无 parent_chunks.pkl 时自动回退到普通模式

**效果**：130 个 parent / 131 个 child，10/10 测试查询命中正确。离线评估来源命中率 @5 从 56.4% 提升到 100%。

## 4. 离线评估体系验证（2026-06-14）

**评估结果对比**：

| 阶段 | 来源命中率 @5 | 关键词命中率 | 说明 |
|------|-------------|-------------|------|
| HashEmbedding 基线 | 23.6% | 38.2% | Demo 级，无语义 |
| DashScope Embedding | 56.4% | — | 有语义但切分粗糙 |
| Parent-Child + 标题注入 | **100%** | **100%** | 当前方案 |

**关键发现**：英文 Reranker（ms-marco-TinyBERT-L-2-v2，~30MB）在中文内容上效果反而变差（100% → 81.8%），已默认关闭。

**Reranker 注意点**：
- 当前 Reranker 用的是英文模型，中文场景不适用
- 中文替代方案：`BAAI/bge-reranker-v2-m3`（~1.1GB），中文效果好，FlashRank 支持 ONNX CPU 推理
- 但模型太大（1GB），Demo 项目不下载，生产环境可部署
- 面试回答："英文 Reranker 在中文上反效果，已关闭。生产环境换中文 BGE-Reranker 或用 Cohere Rerank API"

## 6. LangGraph 多 Agent 架构重构（2026-06-14）

**问题**：
- 状态只有 `messages` 一个字段，路由靠消息体里塞 `__route__` 标记（反模式）
- 意图识别和路由耦合在 supervisor 节点，不可观测
- 缺少回答生成节点（子 Agent 输出直接返回，无格式化/质量检查）
- 缺少兜底节点（出错直接穿透给用户）
- 无 checkpoint，状态不可恢复

**改动**：
- **状态重构**：`AgentState` 从 1 个字段扩展到 7 个结构化字段（messages, intent, route, current_agent, agent_results, error, final_answer）
- **节点拆分**：`supervisor` 拆为 `intent_classifier`（纯意图分类）+ `router`（纯路由决策，无 LLM 调用）
- **新增节点**：`answer_generator`（统一格式化回答）、`fallback`（异常兜底）
- **边重新设计**：所有路由基于 state 字段，不再依赖消息体标记
- **启用 checkpoint**：`MemorySaver` 支持状态恢复

**优化后架构**：
```
intent_classifier → router → ticket_agent → answer_generator → END
                              knowledge_agent ↗         ↓（异常）
                        chat → answer_generator    fallback → END
```

**效果**：10/10 测试通过（图结构、状态定义、路由准确性、链式路由、兜底、意图分类、回答生成、3 个 E2E 端到端测试）。

## 7. LangGraph 延迟优化 + 思考过程可视化（2026-06-14）

**问题**：
- 多节点架构导致 3 次串行 LLM 调用，首 token 延迟（TTFT）~11s
- intent_classifier / router 节点的步骤未推送给前端，用户前 3-5 秒看不到进度

**改动**：
- **answer_generator 单 Agent 透传**：只有 1 个子 Agent 结果时直接返回，不过 LLM（省 ~5-10s）
- **补全节点步骤可视化**：进入每个节点时推送步骤提示（"正在分析您的问题..."、"正在查询票务信息..."等）

**效果**：

| 指标 | 优化前 | 优化后 | 变化 |
|------|--------|--------|------|
| 平均 TTFT | 11.1s | 9.0s | ↓19% |
| 平均总耗时 | 17.5s | 10.5s | ↓40% |
| knowledge 总耗时 | 29.7s | 18.2s | ↓39% |

量化测试 3/3 通过：意图分类准确率 100%、端到端成功率 100%、响应延迟 PASS。

## 8. Java 后端 API 整合（2026-06-15）

**目标**：Python AI 项目与 Java 大麦票务系统打通，支持调用真实业务 API。

**实现方式**：
- 新增 `app/utils/java_api_client.py`：Java API 客户端，支持 HTTP 调用
- 改造 `app/chains/tools.py`：9 个工具支持双模式（Java API / 模拟数据）
- 配置 `java_api_enabled`：True 时调用真实 API，False 时回退到模拟数据

**整合方式**：
- HTTP API 模式：调用 Java 微服务 API（节目服务 6086、订单服务 8081）
- MySQL 直连模式：直接查询 Java 数据库（绕过 ES，数据更完整）

**支持的数据查询**：
- 节目搜索：MySQL 直连 `damai_program_0.d_program_0`（26 条真实数据）
- 节目详情：MySQL 直连 + HTTP API 双模式
- 票档查询：MySQL 直连 `d_ticket_category_0`
- 城市映射：MySQL 直连 `damai_base_data.d_area`（城市名 → area_id）

**测试结果**：
- MySQL 直连：✅ 26 条真实节目数据
- 北京演唱会搜索：✅ 10 条真实结果
- 城市名映射：✅ 北京 → area_id=2
- LangGraph 测试：✅ 10/10 通过
- RAG 评测：✅ Recall@5=100%, Precision=55.7%, MRR=0.992

**面试亮点**：
> "Python AI 项目通过两种方式整合 Java 后端：HTTP API 调用微服务 + MySQL 直连查询数据库（绕过 ES 数据不完整的问题）。支持双模式：Java API 可用时调用真实接口，不可用时回退到模拟数据。通过 MCP 协议封装，第三方客户端也能即插即用。"
