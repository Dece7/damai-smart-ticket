## 核心知识点

### 1. RAG 引用溯源

```
用户: "怎么退票"
    │
    ▼
检索到文档: 【节目取消和退票-相关问题与回答】
    │
    ▼
回答: "退票政策如下...【来源：节目取消和退票-相关问题与回答】"
    │
    ▼
前端: 展示"参考来源"卡片（可折叠，显示文档名 + 摘要）
```

| 环节 | 实现 |
|------|------|
| 检索阶段 | `retriever.invoke()` 返回 Document 对象，含 `metadata.source`💥靠的是元数据 |
| 传递阶段 | SSE 事件 `{type: "sources", content: [{doc, excerpt}]}` |
| 持久化 | messages 表 sources JSON 字段 |
| 前端展示 | 可折叠的"参考来源"卡片，显示文档名和摘要 |

**面试要点：**
- 引用溯源增加可信度，用户可以验证回答是否基于真实文档
- 来源信息随 SSE 事件流传递，前端合并去重后展示
- 持久化到数据库后，切换对话时仍能看到历史来源

**面试问：** RAG 为什么要引用溯源？
**答：** 三个原因：① 增加可信度，用户知道回答有据可查；② 便于验证，发现错误可以定位到具体文档；③ 防止幻觉，LLM 被约束在检索到的文档范围内回答。

### 2. Prompt 注入防护

用正则表达式检测已知的 Prompt 注入模式，chat 和 agent 两个 API 入口都做检查。检测到注入返回 400 错误，输入长度限制 2000 字符。

**面试要点：**
- 正则是最基础的防护（第一道防线），生产环境需要分层叠加：LLM 分类器防语义攻击、System Prompt 约束防角色劫持、输出过滤防提示词泄露
- 正则的局限：变体绕过、多语言攻击、上下文注入
- 特别注意间接注入：恶意指令藏在 RAG 检索到的文档里，比直接注入更难防

> 完整的安全防护方案（输入层/处理层/输出层三层防护、间接注入、工具权限、幻觉检测等）详见 `15-Agent安全防护.md`。

### 3. 多 LLM 调用的延迟优化

**问题**：多个环节都需要 LLM（查询改写、意图分类、注入检测、回答生成），串行调用延迟叠加严重。

```
查询改写 LLM (2s) → 意图分类 LLM (2s) → 子 Agent LLM (5s) → 回答生成 LLM (3s) = 12s+
```

**四种优化思路：**

| 思路 | 做法 | 效果 |
|------|------|------|
| 合并任务 | 多个任务塞进一个 Prompt，一次 LLM 调用 | 减少调用次数 |
| 小模型 | 简单任务用小模型或规则，大模型只做复杂任务 | 降低单次延迟 |
| 并行执行 | 无依赖的任务并行调用 | 降低总延迟 |
| 缓存 | 高频查询缓存结果 | 重复查询 0 延迟 |

**当前项目的实际调用：**

| 任务 | 实现方式 | 是否需要大模型 |
|------|---------|--------------|
| 注入检测 | 正则（0ms） | ❌ |
| 意图分类 | LLM | ✅ |
| 查询改写 | LLM | ⚠️ 可合并到意图分类 |
| 子 Agent | LLM + 工具 | ✅ |
| 回答生成 | LLM | ⚠️ 单 Agent 可透传 |

**面试问：** 多个 LLM 调用串行延迟太长怎么办？
**答：** 四种优化：① 合并任务减少调用次数；② 简单任务用小模型或规则；③ 能并行就并行；④ 缓存高频结果。当前项目注入检测用正则（0ms），真正需要大模型的只有意图分类、子 Agent 和最终回答。

### 4. Token 消耗统计

| 模式 | 统计方式 | 说明 |
|------|---------|------|
| 规则助手 | RAG 链 `usage_metadata` | `llm.invoke()` 返回值携带 |
| 贴心助手 | `invoke` 返回值的 `usage_metadata` | 因 `bind_tools` + `astream` 冲突，改用 `invoke` |
| Agent | `on_chat_model_end` 事件 | LangGraph `astream_events` 捕获每轮 LLM 调用 |
| 多 Agent | `on_chat_model_end` 事件 | 每个子 Agent 节点的 LLM 调用都捕获 |

SSE 事件格式：
```json
{"type": "usage", "content": {"prompt_tokens": 120, "completion_tokens": 85, "total_tokens": 205}}
```

**面试要点：**
- 贴心助手因 `bind_tools` + `stream_usage` 冲突，改用 `invoke` 获取 usage，手动分块推送模拟流式
- 四种模式统计方式不同，因为 LangChain 的链式调用和 LangGraph 的事件机制不同
- Token 数据持久化到 messages 表，支撑管理仪表盘的统计分析

**面试问：** 流式响应怎么获取 Token 用量？
**答：** 两种方式：① 设置 `stream_usage=True`，API 在最后一个 chunk 携带 `usage_metadata`；② 用 `invoke` 代替 `astream`，直接从返回值获取。当前项目因 `bind_tools` 冲突，贴心助手用方式 ②，其他模式用方式 ①。

### 5. Agent 推理可视化

通过 `astream_events` 捕获 Agent 内部事件，SSE 推送到前端，渲染为可折叠的推理时间线。

**四种事件类型：**

| 事件类型 | 含义 | 触发时机 |
|---------|------|---------|
| `node_enter` | 进入新节点 | 多 Agent 模式的节点切换 |
| `reasoning` | LLM 选择工具 | `on_chat_model_end` + 有 tool_calls |
| `tool_start` | 工具开始执行 | `on_tool_start` |
| `tool_end` | 工具返回结果 | `on_tool_end` |

**四种模式的可视化差异：**

| 模式 | 展示内容 | 示例 |
|------|---------|------|
| 规则助手 | 查询改写 | `查询改写：「退票」→「退票政策和退款流程」` |
| 贴心助手 | 工具选择 → 执行 → 返回 | `选择工具: search_program → 执行 → 返回` |
| Agent | 工具选择 → 执行 → 返回 | 同上，ReAct 循环 |
| 多 Agent | 节点进入 + 工具调用 | `正在分配任务... → 正在检索知识库... → 选择工具 → 返回` |

**面试要点：**
- 用 LangGraph 的 `astream_events` 捕获 Agent 内部事件，而非黑盒输出
- 多 Agent 模式多了 `node_enter` 事件，用户能看到"正在分析意图→分配任务→执行→整理回答"的完整流程
- 推理步骤持久化到 `messages.steps` JSON 字段，切换对话时仍可查看
- 前端用可折叠时间线展示，步骤多时默认折叠避免气泡过长

**面试问：** 怎么展示 Agent 的思考过程？
**答：** 用 `astream_events` 捕获四类事件：节点进入、工具选择、工具执行、工具返回，通过 SSE 推送到前端。多 Agent 模式还能展示节点切换过程，让用户看到任务是怎么被分配和执行的。步骤持久化到数据库，切换对话仍可查看。

### 6. 混合检索（BM25 + 向量）

```
用户查询: "退票手续费"
    │
    ├─→ BM25 检索: 关键词匹配 → 返回包含"手续费"的段落
    ├─→ 向量检索: 语义相似 → 返回"退票政策"相关文档
    │
    ▼
RRF 融合排序 → 合并去重 → Top-K
```

```python
# RRF 公式：score = Σ weight / (k + rank)
for rank, doc in enumerate(bm25_results):
    rrf_scores[doc] += bm25_weight / (60 + rank + 1)
for rank, doc in enumerate(vector_results):
    rrf_scores[doc] += (1 - bm25_weight) / (60 + rank + 1)
```

**面试要点：**
- 向量检索擅长语义理解（"退票"能匹配"取消订单"），BM25 擅长关键词精确匹配
- RRF（Reciprocal Rank Fusion）基于排名融合，不需要归一化分数
- BM25 权重 0.9、向量权重 0.1（因 DashScope Embedding 精度有限，BM25 字面匹配更可靠）

**面试问：** BM25 和向量检索各有什么优缺点？
**答：** BM25 基于词频统计，对精确关键词匹配效果好，但无法理解语义相似性；向量检索通过 Embedding 语义编码，能理解同义词和上下文，但对稀有词和专有名词匹配弱。混合互补效果最佳。
