# Function Calling 深度知识点 — 面试要点

> Function Calling 的本质：把自然语言意图，转换成结构化函数调用请求。

---

## 一、Function Calling 解决了什么问题

**一句话**：让大模型从只会聊天，变成能连接外部系统的智能调度器。

```
从 "会说话的大脑" → "能调度系统的大脑"
```

核心变化：模型不再凭空猜，而是通过工具拿到真实世界的数据。

---

## 二、核心角色分工

| 角色 | 职责 | 类比 |
|------|------|------|
| **大模型** | 意图识别、工具选择、参数抽取、组织回复 | 聪明前台 + 表达组织者 |
| **应用层** | 接收 tool_call、执行函数、返回结果 | 真正执行者 |
| **工具 Schema** | 告诉模型有哪些工具、需要什么参数 | 工具说明书 |

完整链路：

```
用户: "北京今天天气怎么样"
  ↓
大模型（前台）: 判断要调用 get_weather(city="北京")
  ↓ 输出 tool_call（结构化 JSON）
应用层: 接收 tool_call → 调用真实 API → 返回结果
  ↓
大模型（组织者）: "北京今天晴，25°C，适合出行~"
```

**关键点**：模型输出的是 `tool_call`（结构化指令），不是自然语言，所以应用层能可靠解析。

---

## 三、模型怎么知道该调用哪个函数

**答案**：先给模型一本"工具说明书"——Function Schema。

### Function Schema 示例

```json
{
  "name": "get_weather",
  "description": "根据城市查询天气",
  "parameters": {
    "type": "object",
    "properties": {
      "city": {
        "type": "string",
        "description": "城市名称"
      }
    },
    "required": ["city"]
  }
}
```

### 关键点

- 不是把 Java 方法直接丢给模型
- 而是用 JSON Schema 一类的结构，告诉模型：这个工具能干什么、需要哪些参数、哪些字段必填

### 本项目

```python
@tool
def search_program(city: str, category: str = None) -> str:
    """搜索演出信息，根据城市和类型查询

    Args:
        city: 城市名称，如"北京"、"上海"
        category: 演出类型，如"演唱会"、"话剧"
    """
    ...
```

`@tool` 装饰器自动生成 Schema，`docstring` 就是工具描述。

---

## 四、底层原理（重点记忆）

> Function Calling 的底层不是模型真的执行代码，而是模型基于上下文和函数 Schema 完成**意图识别、工具选择和参数抽取**，然后输出一个结构化的 tool call，由应用程序真正执行函数。

```
用户输入 + 工具 Schema
  ↓
意图识别: 用户想干什么？
  ↓
工具选择: 应该调用哪个函数？
  ↓
参数抽取: 需要传什么参数？
  ↓
输出 tool_call: {"name": "get_weather", "arguments": {"city": "北京"}}
  ↓
应用层执行: 调用真实 API
  ↓
结果回传: "北京晴，25°C"
  ↓
模型组织回复: "北京今天天气很好~"
```

---

## 五、Function Calling 和普通 Prompt 的区别

**核心差别：稳定、可控、结构化、和外部系统交互。**

| 维度 | 普通 Prompt | Function Calling |
|------|------------|-----------------|
| 格式 | 不稳定，可能多说废话 | 稳定输出结构化 JSON |
| 工具名 | 可能胡编 | 必须在白名单内 |
| 参数 | 可能缺失或格式错 | 有 Schema 校验 |
| 工程落地 | 难解析、难兜底 | 可解析、可校验、可管控 |

普通 Prompt 的问题：

```
用户: "帮我查北京天气"
模型: "好的，我来帮你查一下北京的天气，北京今天晴天，25度..."
问题: 回答里混了自然语言，应用层很难解析出结构化数据
```

Function Calling 的结果：

```json
{
  "tool_calls": [
    {
      "name": "get_weather",
      "arguments": {"city": "北京"}
    }
  ]
}
```

**它解决的不是"让模型说出函数名"，而是让模型和系统之间建立一套可解析、可校验、可管控的交互协议。**

## 六、会不会调用错函数

**会。大模型不是规则引擎，真实项目里必须做工程兜底。**

### 四大兜底措施

| 措施 | 说明 | 示例 |
|------|------|------|
| **函数白名单** | 模型只能调用后端允许的函数 | 只注册了 9 个工具，其他一律拒绝 |
| **参数校验** | 类型、格式、权限都要校验 | 订单号必须是数字，金额必须 > 0 |
| **敏感操作确认** | 删数据、付款等需要二次确认 | "确认要下单吗？" |
| **异常处理** | 超时、错误要返回给模型生成解释 | "订单查询失败，请稍后重试" |

### 本项目的兜底

```python
# 白名单：只注册 9 个工具
ALL_TOOLS = [
    search_program, get_program_detail, get_ticket_info, create_order,
    query_ticket_status, check_order_status, calculate_price, get_recommendations,
    search_knowledge_base,
]

# 异常处理：工具执行失败，返回错误信息给模型
try:
    result = tool.invoke(args)
except Exception as e:
    result = f"工具执行失败: {e}"

# 模型基于错误信息生成用户友好的回答
```

**重点记忆：真实落地不是"调个 API"这么简单，而是一套安全可控的工程系统。**

## 七、Function Calling 的本质（一句话）

> Function Calling 就是大模型与现实世界之间的接口。

---

## 八、面试金句

> "Function Calling 的本质不是大模型真的执行函数，而是开发者先把可用函数以 schema 的形式告诉模型；模型根据用户意图选择函数并生成结构化参数；应用层接收到 tool call 后真正执行函数，再把结果回传给模型，由模型组织最终回复。"

---

## 九、本项目 Function Calling 实践

| 环节 | 实现 |
|------|------|
| 工具定义 | `@tool` 装饰器，9 个业务工具 |
| Schema 生成 | 自动生成 JSON Schema（从 docstring + 类型注解） |
| 工具绑定 | `llm.bind_tools(ALL_TOOLS)` |
| 意图识别 | 模型自动判断调用哪个工具 |
| 参数抽取 | 模型自动从用户问题中提取参数 |
| 执行 | 应用层调用真实函数 |
| 结果回传 | 工具返回值传回模型 |
| 回复组织 | 模型基于工具结果生成自然语言回答 |
| 兜底 | 白名单 + 参数校验 + 异常处理 |
