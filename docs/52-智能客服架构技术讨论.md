# 智能客服架构技术讨论

> 智能客服项目中常用的架构模式分析与对比，包括Router-Skill、ReAct、Graph Workflow等。

---

## 一、当前项目使用的架构

### 1.1 架构清单

| 模式 | 架构 | 特点 | 适用场景 |
|------|------|------|----------|
| **Agent** | ReAct | 自由发挥，思考→行动→观察循环 | 复杂推理任务 |
| **多Agent** | Graph Workflow | 多Agent协作，6节点结构化编排 | 复杂流程任务 |
| **贴心助手** | Function Calling | 单轮工具调用 | 简单任务 |
| **规则助手** | RAG | 知识库问答 | 规则咨询 |
| **智能助手** | Router-Skill | 做选择题，从预定义Skill中选择 | 生产环境 |

### 1.2 ReAct架构

**核心思想**：思考→行动→观察的循环

```
用户提问
  ↓
思考：用户想查北京演唱会
  ↓
行动：调用 search_program(city="北京", category="演唱会")
  ↓
观察：返回5个演唱会
  ↓
思考：用户可能想买票
  ↓
行动：调用 create_order_guide(program_id=4)
  ↓
观察：返回购票链接
  ↓
回答：为您找到以下演唱会...[购票卡片]
```

**特点**：
- 循环执行：思考→行动→观察
- 可以多轮工具调用
- 但容易"过度思考"或"瞎想"

---

### 1.3 Graph Workflow（图工作流）

**核心思想**：使用状态图定义工作流

```
用户提问
  ↓
意图分类器 → 路由
  ├→ ticket_agent（票务专家）
  ├→ knowledge_agent（知识库专家）
  └→ answer_generator（回答生成）
```

**特点**：
- 使用LangGraph实现
- 支持条件路由、循环、分支
- 适合复杂流程任务

**代码示例**：
```python
from langgraph.graph import StateGraph, END

# 定义状态
class AgentState(TypedDict):
    messages: list
    intent: str
    route: str
    agent_results: dict
    final_answer: str

# 构建图
workflow = StateGraph(AgentState)
workflow.add_node("intent_classifier", intent_classifier_node)
workflow.add_node("router", router_node)
workflow.add_node("ticket_agent", ticket_agent_node)
workflow.add_node("knowledge_agent", knowledge_agent_node)
workflow.add_node("answer_generator", answer_generator_node)

# 添加边
workflow.add_edge("intent_classifier", "router")
workflow.add_conditional_edges("router", route_after_router)
workflow.add_edge("ticket_agent", "answer_generator")
workflow.add_edge("knowledge_agent", "answer_generator")
workflow.add_edge("answer_generator", END)

# 编译
graph = workflow.compile()
```

## 二、Router-Skill架构

### 2.1 核心思想

**让模型做选择题，而不是自由发挥！**

```
用户提问 → Router（路由器）
              ↓
         从预定义的Skill中选择
              ↓
         执行选中的Skill
              ↓
         返回结果
```

### 2.2 架构组成

```
┌─────────────────────────────────────────────────────────────┐
│                    Router-Skill 架构                        │
├─────────────────────────────────────────────────────────────┤
│                                                             │
│  1. Skill（技能层）                                         │
│     ├─ 预定义的输入输出格式                                │
│     ├─ 独立的功能单元                                      │
│     ├─ 可复用、可测试                                      │
│     └─ 不依赖LLM                                           │
│                                                             │
│  2. Router（路由层）                                        │
│     ├─ 接收用户问题                                         │
│     ├─ 从预定义Skill中选择最合适的                          │
│     └─ 提取参数                                             │
│                                                             │
│  3. ResponseGenerator（回复生成层）                         │
│     ├─ 格式化输出                                           │
│     └─ 生成用户友好的回复                                   │
│                                                             │
└─────────────────────────────────────────────────────────────┘
```

### 2.3 Skill的本质

Skill是一堆提示词 + 方法调用的组合：

```python
class SearchProgramSkill(Skill):
    """搜索节目技能"""
    
    @property
    def name(self) -> str:
        return "search_program"
    
    @property
    def description(self) -> str:
        return "根据城市、类型或艺人搜索节目"
    
    @property
    def parameters(self) -> dict:
        return {
            "type": "object",
            "properties": {
                "city": {"type": "string", "description": "城市名"},
                "category": {"type": "string", "description": "节目类型"},
            }
        }
    
    def execute(self, city: str = "", category: str = "") -> dict:
        """执行搜索 - 调用全栈项目API"""
        result = java_api.search_program(city=city, category=category)
        return result or {"totalSize": 0, "list": []}
```

### 2.4 Router的工作原理

```python
class Router:
    """路由器"""
    
    def route(self, user_message: str) -> tuple[str, dict, float]:
        """路由到合适的技能"""
        # 构建选择题
        prompt = f"""
        用户问题：{user_message}
        
        可用的技能：
        1. search_program - 搜索节目
        2. get_order_list - 查询订单列表
        3. search_knowledge_base - 搜索知识库
        4. create_order_guide - 下单引导
        
        请选择最合适的技能，并提供参数。
        """
        
        # LLM做选择题
        response = self.llm.invoke(prompt)
        
        # 解析选择
        skill_name, params = self.parse_response(response)
        
        return skill_name, params
```

## 三、Router-Skill vs ReAct 架构对比

### 3.1 核心区别

| 维度 | ReAct架构 | Router-Skill架构 |
|------|----------|-----------------|
| **模型角色** | 自由发挥 | 做选择题 |
| **工具选择** | 从N个工具中自由选择 | 从预定义Skill中选择 |
| **参数提取** | LLM自己提取 | LLM从选择题中提取 |
| **执行流程** | 思考→行动→观察（循环） | 路由→执行→回复（单次） |
| **可控性** | 低（可能选错） | 高（只能选预定义的） |
| **可预测性** | 低 | 高 |

### 3.2 详细对比

**ReAct架构**：
```
用户："帮我查北京的演唱会，顺便告诉我退票政策"
  ↓
思考：用户想查演唱会和退票政策
  ↓
行动：调用 search_program(city="北京")
  ↓
观察：返回5个演唱会
  ↓
思考：还需要查退票政策
  ↓
行动：调用 search_knowledge_base(query="退票")
  ↓
观察：返回退票政策
  ↓
回答：整合两个结果
```

**Router-Skill架构**：
```
用户："帮我查北京的演唱会，顺便告诉我退票政策"
  ↓
Router：选择 search_program 或 search_knowledge_base？
  ↓
选择：search_program（只能选一个）
  ↓
执行：返回演唱会列表
  ↓
回答：只回答了演唱会，没有回答退票政策
```

### 3.3 代码对比

**ReAct架构**：
```python
# 自由发挥，可能选错工具
agent = create_react_agent(
    model=llm,
    tools=ALL_TOOLS,  # 9个工具全部给Agent
    prompt=SYSTEM_PROMPT,
)
```

**Router-Skill架构**：
```python
# 做选择题，只能选预定义的Skill
router = Router(skills={
    "search_program": SearchProgramSkill(),
    "get_order_list": GetOrderListSkill(),
    "create_order_guide": CreateOrderGuideSkill(),
    "search_knowledge_base": SearchKnowledgeSkill(),
})
```

## 四、Router-Skill的问题与解决方案

### 4.1 问题1：多需求任务处理能力弱

**示例**：
```
用户："帮我查北京的演唱会，顺便告诉我退票政策"
```

**Router-Skill的处理**：
- 只能选择一个Skill
- 可能只回答了演唱会，没有回答退票政策

**解决方案**：支持多Skill选择

```python
# 修改Router提示词
ROUTER_PROMPT = """...
请以JSON格式输出，包含以下字段：
1. "skills": 选择的技能列表（可以多个）
2. "parameters": 每个技能的参数

示例输出：
{
  "skills": [
    {"name": "search_program", "parameters": {"city": "北京"}},
    {"name": "search_knowledge_base", "parameters": {"query": "退票"}}
  ]
}
"""
```

### 4.2 问题2：上下文理解能力弱

**示例**：
```
用户："帮我查北京的演唱会"
AI："找到了5个演唱会..."
用户："第二个多少钱？"
```

**Router-Skill的处理**：
- 不理解"第二个"是什么
- 可能重新搜索"第二个"

**解决方案**：结合对话历史

```python
def route(self, user_message: str, history: list) -> tuple:
    """路由时考虑对话历史"""
    prompt = f"""
    对话历史：{history}
    用户问题：{user_message}
    
    请选择最合适的技能...
    """
```

### 4.3 问题3：复杂任务处理能力弱

**示例**：
```
用户："帮我买周杰伦演唱会的票，要2张看台A区"
```

**Router-Skill的处理**：
- 可能只调用create_order_guide
- 没有先查询节目信息和票档信息

**解决方案**：Skill组合

```python
class SearchAndGuideSkill(Skill):
    """搜索并引导购票"""
    
    def execute(self, city: str, category: str) -> dict:
        # 1. 搜索节目
        programs = java_api.search_program(city=city, category=category)
        
        # 2. 如果只有一个节目，直接生成购票链接
        if len(programs) == 1:
            program = programs[0]
            return {
                "type": "buy_guide",
                "program_id": program["id"],
                "buy_url": f"http://localhost:5173/contentDetail/index/{program['id']}"
            }
        
        # 3. 如果有多个节目，返回列表让用户选择
        return {
            "type": "program_list",
            "programs": programs
        }
```

## 五、企业级客服项目架构选择

### 5.1 主流架构对比

| 架构 | 使用场景 | 代表项目 | 优势 |
|------|----------|----------|------|
| **Router-Skill** | 简单任务 | 阿里小蜜、京东JIMI | 可控、可测试 |
| **Graph Workflow** | 复杂任务 | 字节Coze、腾讯混元 | 灵活、可扩展 |
| **ReAct** | 推理任务 | ChatGPT Plugins | 强推理能力 |
| **混合架构** | 综合场景 | 企业级客服系统 | 兼顾各种需求 |

### 5.2 企业级客服项目的典型架构

```
┌─────────────────────────────────────────────────────────────┐
│                    企业级客服架构                            │
├─────────────────────────────────────────────────────────────┤
│                                                             │
│  用户提问                                                    │
│     ↓                                                       │
│  ┌─────────────────────────────────┐                       │
│  │  意图识别层                      │                       │
│  │  ├─ 简单意图 → Router-Skill     │                       │
│  │  ├─ 复杂意图 → Graph Workflow   │                       │
│  │  └─ 推理任务 → ReAct            │                       │
│  └─────────────┬───────────────────┘                       │
│                ↓                                            │

│  │  执行层                          │                       │
│  │  ├─ 查询类：直接API调用          │                       │
```

### 5.3 为什么Router-Skill仍然是主流？

**原因1：80/20法则**

```
80%的问题是简单问题：
├─ 查询节目信息
├─ 查询订单状态
├─ 查询退票政策
└─ 查询票价信息

20%的问题是复杂问题：
├─ 多步骤任务
├─ 复杂推理
└─ 异常处理

Router-Skill可以处理80%的简单问题，
剩下的20%可以用其他架构处理。
```

**原因2：成本控制**

```
Router-Skill：
├─ 1次LLM调用（路由）
├─ 1次Skill执行
└─ 总成本：低

ReAct：
├─ N次LLM调用（思考）
├─ N次工具执行
└─ 总成本：高

企业级项目需要控制成本，Router-Skill更经济。
```

**原因3：可维护性**

```
Router-Skill：
├─ 代码结构清晰
├─ 每个Skill独立
├─ 易于测试
└─ 易于维护

ReAct：
├─ 代码结构复杂
├─ 工具调用不可预测
├─ 难以测试
└─ 难以维护

企业级项目需要团队协作，Router-Skill更易维护。
```

## 八、面试话术

### 8.1 项目介绍

> "我了解多种智能客服架构：单Agent、ReAct、多Agent、Router-Skill、Graph Workflow。当前项目使用LangGraph实现了Graph Workflow，包含6节点结构化编排。如果要做生产级，我会考虑引入Router-Skill架构，让模型做选择题而不是自由发挥，提高可控性和可预测性。"

### 8.2 架构对比

> "Router-Skill和ReAct的核心区别在于：Router-Skill让模型做选择题，从预定义的Skill中选择；ReAct让模型自由发挥，自己决定调用哪个工具。Router-Skill的优势是可控性高、可测试、可维护；ReAct的优势是支持复杂推理和多轮工具调用。企业级项目大多采用混合架构：简单任务用Router-Skill，复杂任务用Graph Workflow。"

### 8.3 技术选型

> "选择架构时需要考虑几个因素：任务类型、可控性要求、成本预算、团队能力。对于简单任务，Router-Skill是最佳选择，因为可控性高、成本低、易维护。对于复杂任务，需要使用Graph Workflow或ReAct。实际项目中，我会采用混合架构，根据任务类型选择合适的架构。"
