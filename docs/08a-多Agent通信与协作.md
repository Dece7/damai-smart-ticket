# 多 Agent 通信与协作 — 知识点与面试要点

> 多 Agent 协作的本质就是"分工协作"。Agent 不是越多越好，而是让复杂任务变得更有组织。

---

## 一、多 Agent 的本质

### 四种模式的比喻

```
贴心助手：只有锤子，什么都当钉子敲
规则助手：只有尺子，什么都想量一量
Agent：  工具箱全给，自己选
多 Agent：先分类，再派专业的人干专业的事
```

### 一句话理解

一个 Agent 像一个员工，多个 Agent 协作就像一个小团队一起干活。

```
研究员搜资料 → 分析师提观点 → 编辑写内容 → 审稿人查逻辑 → 设计师转PPT
```

### 单 Agent 的问题

任务一复杂，就要同时扮演研究、分析、写作、审核、排版多个角色，容易混乱、遗漏、前后不一致。

### 多 Agent 的思路

把复杂任务拆开，每个 Agent 只负责一个明确角色，最后再进行整合与审核。

### 本项目

```
intent_classifier（分析意图）
  → router（路由决策）
    → ticket_agent（票务专家，8 个工具）
    → knowledge_agent（知识库专家，1 个工具）
    → answer_generator（整合回答）
    → fallback（异常兜底）
```

## 二、三种主要通信方式

### 方式一：顺序传递

```
A 做完交给 B，B 做完交给 C
```

像流水线，适合标准化任务。

| 维度 | 说明 |
|------|------|
| 适用场景 | 写报告、做方案、整理纪要、竞品分析 |
| 关键 | 每一环要有结构化输出和质量标准 |
| 优点 | 流程清楚、稳定可控；适合标准化任务；便于定位每一步的责任 |
| 风险 | 前面 Agent 一旦错，后面很容易一路错下去，形成错误放大 |
| 解决 | 每一环必须定义输入、输出格式、质量标准和不确定性标注 |

**本项目用的就是这种**：supervisor → ticket_agent → knowledge_agent → answer_generator

### 方式二：共享黑板

```
所有 Agent 围绕同一个共享上下文工作
```

像团队共用一块白板。

| 维度 | 说明 |
|------|------|
| 适用场景 | 产品设计、商业策划、战略分析 |
| 关键 | 要有协调者管理黑板 |
| 优点 | Agent 可以看到其他 Agent 的进展，灵活协作 |
| 风险 | 没有管理，就会变成信息垃圾场 |

### 方式三：消息对话

```
Agent 根据问题动态问答、反馈、澄清
```

| 维度 | 说明 |
|------|------|
| 适用场景 | 代码开发、客服处理、法律审核、项目规划 |
| 关键 | 要限制轮次、定义决策权和停止条件 |
| 优点 | 更灵活，不必固定 A→B→C，可根据问题临时问答与修正 |
| 风险 | 如果没有规则，会来回讨论、陷入循环，成本越来越高 |

### 三种方式对比

| 方式 | 流程 | 灵活性 | 复杂度 | 适用 |
|------|------|--------|--------|------|
| 顺序传递 | 固定 | 低 | 低 | 标准化任务 |
| 共享黑板 | 半固定 | 中 | 中 | 协作型任务 |
| 消息对话 | 动态 | 高 | 高 | 复杂交互任务 |

## 三、协作边界

**协作边界 = 决策权 + 轮次限制 + 停止条件 + 不确定性标注**

| 边界 | 说明 | 示例 |
|------|------|------|
| **决策权** | 谁有最终决定权 | supervisor 决定路由，子 Agent 不能自己跳转 |
| **轮次限制** | 最多执行几轮 | 本项目工具调用最多 5 轮 |
| **停止条件** | 什么时候结束 | LLM 没有 tool_calls 时停止 |
| **不确定性标注** | 不确定时怎么处理 | 子 Agent 不确定时返回"无法判断"，不编造 |

### 本项目的边界设计

```python
# 决策权：supervisor 有路由决策权
def route_after_supervisor(state):
    return state["route"]  # 读 state 字段，不靠消息标记

# 停止条件：answer_generator 执行完就结束
graph.add_edge("answer_generator", END)

# 异常兜底：出错走 fallback
graph.add_conditional_edges("ticket_agent", route_after_ticket, {
    "knowledge_agent": "knowledge_agent",
    "answer_generator": "answer_generator",
    "fallback": "fallback",  # 异常路径
})
```

## 四、常见误区

### 误区一：Agent 越多越好

**错**。Agent 越多，沟通成本越高，状态管理越复杂，出错点也越多。

```
3 个 Agent：3 条通信路径
5 个 Agent：10 条通信路径
10 个 Agent：45 条通信路径
```

### 误区二：多 Agent 一定比单 Agent 好

**错**。简单任务用单 Agent 更高效，多 Agent 只在复杂任务时有优势。

| 任务复杂度 | 推荐方案 |
|-----------|---------|
| 简单（闲聊、单一工具调用） | 单 Agent |
| 中等（需要 2-3 个工具协作） | 单 Agent 或 2 个子 Agent |
| 复杂（多角色、多步骤、需要审核） | 多 Agent |

### 误区三：子 Agent 之间不需要定义接口

**错**。子 Agent 之间必须定义清晰的输入输出格式，否则结果无法整合。

## 五、多 Agent 系统的设计原则

| 原则 | 说明 |
|------|------|
| **职责单一** | 每个 Agent 只负责一件事 |
| **接口清晰** | 输入输出格式明确，便于串联 |
| **边界可控** | 决策权、轮次、停止条件都有定义 |
| **异常兜底** | 任何 Agent 出错都有 fallback 处理 |
| **可观测** | 每一步的状态都可以追踪 |

## 七、面试高频问题

| 问题 | 回答要点 |
|------|---------|
| 多 Agent 和单 Agent 的区别？ | 单 Agent 一个角色做所有事，多 Agent 分工协作，每个 Agent 只负责一件事 |
| 多 Agent 怎么通信？ | 三种方式：顺序传递、共享黑板、消息对话 |
| 多 Agent 的风险？ | Agent 越多沟通成本越高，前面错了后面跟着错，需要定义协作边界 |
| 怎么定义协作边界？ | 决策权 + 轮次限制 + 停止条件 + 不确定性标注 |
| Agent 越多越好吗？ | 不是，Agent 越多状态管理越复杂，简单任务用单 Agent 更高效 |
| 子 Agent 之间怎么传数据？ | 共享状态（LangGraph AgentState）、消息传递、黑板模式 |
| 你项目用什么通信方式？ | 顺序传递 + 共享状态，agent_results 字典汇聚各子 Agent 结果 |
| 多 Agent 一定比单 Agent 好吗？ | 不一定，简单任务单 Agent 更高效，复杂任务才需要多 Agent |

## 八、面试话术

> "多 Agent 的本质是分工协作，把复杂任务拆成小团队。三种主要通信方式：顺序传递（流水线）、共享黑板（共用白板）、消息对话（动态问答）。我项目用的是顺序传递 + 共享状态模式，supervisor 分析意图后路由到专业子 Agent，各子 Agent 把结果写入 agent_results 字典，answer_generator 读取所有结果做整合。协作边界很重要——决策权、轮次限制、停止条件、不确定性标注，缺一不可。Agent 不是越多越好，越多沟通成本越高，简单任务用单 Agent 更高效。"
