# 面试建议

> 小麦同学智能AI客服项目的技术选型对比、面试高频问题及回答准备。

---

## 一、技术选型：最小实现 vs 生产级

面试官可能会问 " **为什么用 xxx 而不是 yyy？** " ，以下是项目中各模块的选型对比和回答思路。

| 模块 | 当前选型（最小实现） | 生产级选型 | 选择原因 |
|------|-------------------|-----------|---------|
| **Embedding** | HashEmbedding（随机哈希） | DashScope Embedding / BGE-M3 | HashEmbedding 是 demo 级，零成本验证流程；生产环境换模型只改配置不改代码 |
| **向量库** | ChromaDB（嵌入式） | Milvus / Qdrant / Weaviate | ChromaDB 零部署、适合单机；生产环境数据量大（百万级）应用 Milvus |
| **Reranker** | FlashRank 已关闭（英文模型对中文反效果） | BGE-Reranker-v2-m3（中文）/ Cohere Rerank | 英文 Reranker 在中文上效果差（100%→81.8%），已关闭；生产环境换中文模型 |
| **数据库** | SQLite | PostgreSQL / MySQL | SQLite 零部署、单写多读；生产环境高并发应用 PostgreSQL |
| **数据源** | Mock 模拟数据 | 真实数据库 + 外部 API | Mock 数据用于 demo；工具层抽象，换数据源只改实现不改 Agent 逻辑 |
| **缓存** | 无 | Redis | 热门问题缓存检索结果和 LLM 回答，减少重复计算 |
| **监控** | 自建 Token 统计 | LangSmith / LangFuse | 自建统计够用；LangSmith 支持 Agent 调用链追踪，生产环境更完整 |
| **部署** | Docker Compose | K8s + HPA | Docker Compose 适合单机；K8s 支持自动扩缩容、滚动更新 |

## 二、面试高频问题及回答

### Embedding 相关

**Q: HashEmbedding 精度够吗？**

> HashEmbedding 是 demo 级实现，精度很低（来源命中率 23.6%）。生产环境用 DashScope Embedding（阿里云），精度提升到 56%+。再加上 Parent-Child 分块和标题注入优化，来源命中率提升到 100%。项目设计上 Embedding 是可替换的，通过配置切换模型，换模型只改配置不改代码。

**Q: 为什么不用 OpenAI Embedding？**

> 项目面向国内市场，DashScope Embedding（阿里云）和 BGE-M3 中文效果更好、成本更低。OpenAI Embedding 需要海外 API 访问，延迟高且有合规风险。

**Q: Embedding 模型怎么选？**

> 看三个维度：① 中文效果（BGE-M3 > DashScope Embedding > OpenAI）；② 成本（DashScope 有免费额度）；③ 部署方式（BGE-M3 可本地部署，DashScope 需要 API）。项目选择 DashScope Embedding 是因为有免费额度、中文效果好、API 调用简单。

---

### 向量库相关

**Q: 为什么用 ChromaDB 而不是 Milvus？**

> ChromaDB 是嵌入式向量库，零部署、Python 原生支持、适合开发和小规模场景；Milvus 是分布式向量库，支持十亿级向量、高可用、水平扩展。项目当前是 demo 阶段，ChromaDB 够用；生产环境如果数据量大（百万级以上），应该用 Milvus 或 Qdrant。

**Q: ChromaDB 和 FAISS 的区别？**

> FAISS 是 Facebook 开源的向量检索库，纯算法库、需要自己管理存储和索引；ChromaDB 是完整的向量数据库，内置持久化、元数据过滤、自动索引。项目选择 ChromaDB 是因为它更易用，内置持久化不需要额外处理。

**Q: 向量库怎么选型？**

> 看数据规模和部署方式：① 小规模（<100 万）单机用 ChromaDB；② 中等规模（100 万 - 1000 万）用 Qdrant（Rust 实现，性能好）；③ 大规模（>1000 万）用 Milvus（分布式架构）。项目选择 ChromaDB 是因为数据量小（131 个分块），不需要分布式。

---

### Reranker 相关

**Q: FlashRank 和 BGE-Reranker 有什么区别？**

> FlashRank 是轻量级 Reranker（~30MB），CPU 友好、推理快（~80ms），适合低延迟场景；BGE-Reranker 是交叉编码器（~1.1GB），精度更高但需要 GPU 或 CPU 推理较慢（~500ms）。项目选择 FlashRank 是因为部署环境是 CPU，需要低延迟。

**Q: Reranker 和 Embedding 的区别？**

> Embedding 是双塔模型，query 和 doc 独立编码成向量，用余弦相似度比较，速度快但精度有限；Reranker 是交叉编码器，query 和 doc 联合编码，计算 token 级别交互特征，精度更高但速度慢。最佳实践是先用 Embedding 粗排取 Top-20，再用 Reranker 精排取 Top-5。

**Q: 为什么需要 Reranker？**

> 粗排（向量+BM25）效率高但精度有限，Reranker 用交叉编码器做精排，计算 query-doc 交互特征，精度更高。但当前项目实测发现，英文 Reranker（ms-marco-TinyBERT-L-2-v2）用在中文内容上效果反而变差（81.8% → 100% 关闭后），所以默认关闭。生产环境需要换中文 Reranker（如 BGE-Reranker）才能发挥精排效果。

---

### 数据库相关

**Q: SQLite 支持并发吗？**

> SQLite 是文件级数据库，支持读并发但写并发有限（单写多读）。项目当前是单实例部署，SQLite 够用。如果需要多实例部署或高并发写入，应该用 PostgreSQL。SQLite 的优点是零部署、数据文件即备份。

**Q: 为什么不用 MySQL？**

> SQLite 更轻量，零部署、不需要单独的数据库服务。项目是单机部署，SQLite 够用。如果需要多实例部署或复杂查询，应该用 PostgreSQL（比 MySQL 功能更强、支持 JSON 类型）。

---

### 数据源相关

**Q: Mock 数据和真实数据有什么区别？**

> Mock 数据是预定义的字典，用于 demo 演示；真实数据需要对接数据库（MySQL/PostgreSQL）、调用外部 API（大麦网接口）。项目设计上工具层是抽象的（@tool 装饰器），换数据源只改工具实现，不改 Agent 逻辑。

**Q: 怎么对接真实数据？**

> 工具层是抽象的，只需要修改工具函数内部实现。比如 `search_program` 工具，把 mock 数据替换为 SQL 查询或 API 调用即可。Agent 层不需要任何修改。

---

### 监控相关

**Q: 为什么不用 LangSmith？**

> LangSmith 是 LangChain 官方的可观测性平台，支持 Agent 调用链追踪、Token 统计、错误监控。项目自建了 Token 统计和推理可视化，功能上够用，但缺少调用链追踪。如果项目规模增大，应该接入 LangSmith 或 LangFuse（开源替代品）。

**Q: LangSmith 和 LangFuse 有什么区别？**

> LangSmith 是 LangChain 官方产品，功能最全但收费；LangFuse 是开源替代品，功能类似但社区支持。项目选择自建统计是因为 demo 阶段不需要完整的可观测性平台。

---

### MCP 相关

**Q: MCP 和 Function Calling 有什么区别？**

> Function Calling 是 LLM 层面的机制，LLM 决定调用哪个工具、传什么参数；MCP 是传输层的标准化协议，定义工具怎么暴露、怎么连接、怎么调用。两者互补：Function Calling 负责"选哪个工具"，MCP 负责"工具怎么接入"。

**Q: MCP 和 API 网关有什么区别？**

> MCP 是 AI 领域的工具协议，包含工具发现、参数描述、调用语义；API 网关是通用的 HTTP 代理，负责路由、认证、限流。MCP 专注于 AI 工具调用场景，API 网关专注于通用 API 管理。

**Q: 为什么要做 MCP？**

> 将现有工具封装为 MCP Server，第三方客户端（Claude Desktop、Cursor）即插即用。体现了工程前瞻性，MCP 是 2025 年的新趋势。

---

### 多 Agent 相关

**Q: 多 Agent 和单 Agent + 多工具的区别？**

> 多 Agent 有独立的 system prompt 和工具集，决策更精准；单 Agent 所有工具混在一起，容易选错。比如问"会员有什么等级"，单 Agent 可能调用 search_program（搜演出），多 Agent 的知识库 Agent 只会调用 search_knowledge_base。

**Q: 多 Agent 模式怎么工作？**

> 6 节点结构化编排：intent_classifier（意图分类）→ router（路由决策）→ 子 Agent（ticket_agent / knowledge_agent）→ answer_generator（整合回答）→ fallback（异常兜底）。路由基于结构化 State 字段，不用消息体标记。

**Q: 子 Agent 之间怎么通信？**

> 通过共享 State（agent_results 字典）传递结果。子 Agent 各自把结果写入 agent_results，answer_generator 读取所有结果做整合。子 Agent 之间不直接通信，避免耦合。

---

### 查询改写相关

**Q: 查询改写和 HyDE 有什么区别？**

> HyDE 生成假设性回答，用回答做检索；Query Rewriting 改写问题本身，更直接可控。HyDE 依赖生成质量，Query Rewriting 更稳定。项目选择 Query Rewriting 是因为实现简单、效果稳定。

**Q: 查询改写延迟多少？**

> 用 Mimo 模型做改写，~100ms 延迟。如果原始问题已经足够清晰，直接返回原问题，不增加延迟。

---

### RAG 相关

**Q: BM25 和向量检索各有什么优缺点？**

> BM25 基于词频统计，对精确关键词匹配效果好，但无法理解语义相似性；向量检索通过 Embedding 语义编码，能理解同义词和上下文，但对稀有词和专有名词匹配弱。混合互补效果最佳。

**Q: RRF 融合公式是什么？**

> score = Σ weight / (60 + rank)，基于排名的加权融合。BM25 权重 0.9，向量权重 0.1（因为 HashEmbedding 精度低，所以 BM25 权重高）。

**Q: RAG 系统怎么评估？**

> 分层评估：① 检索质量（Recall@5=100%、Precision@5=55.7%、MRR=0.992）；② 生成质量（LLM Judge 4.9/5，忠实度 5.0 无幻觉）；③ 端到端（延迟 320ms）。项目有 65 条测试用例，覆盖 knowledge、ticket、both 三种意图。

---

### 前端相关

**Q: 为什么用 Vite 而不是 Webpack？**

> Vite 基于 ESBuild 原生 ESM，开发启动秒级；Webpack 需要打包，启动慢。Vite 是 Vue 3 官方推荐的构建工具。

**Q: 为什么用 Pinia 而不是 Vuex？**

> Pinia 是 Vuex 5，支持 TypeScript、组合式 API、去 mutations。Pinia 更轻量、类型安全更好，是 Vue 3 官方推荐的状态管理方案。

**Q: SSE 流式怎么在 Vue 中处理？**

> fetch + ReadableStream，逐 token 追加到消息对象，Vue 响应式更新。不用 EventSource 是因为需要 POST 请求和自定义 Header。
