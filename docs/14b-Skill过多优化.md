# Skill 数量过多时如何保证命中率

> Skill 不是越多越好。Skill 越多，description 之间的重叠越多，系统越难区分，误命中率越高。核心是信噪比问题。

---

## 一、问题本质

**面试提问**：Skill 数量多了之后，命中率下降怎么办？

💥**优质回答**💥：
> Skill 越多，description 之间的重叠越多，系统越难区分。本质是**信噪比问题**。
>
> 解决思路是让每个 Skill 的边界更清晰、选择过程更高效。

```
5 个 Skill 时：
  用户说"我要退票" → 系统在 5 个 description 里找匹配 → 容易命中

50 个 Skill 时：
  用户说"我要退票" → 系统在 50 个 description 里找匹配 →
  "退款 skill"和"订单 skill"和"投诉 skill"都沾点边 → 选哪个？
```

---



## 二、四个解决思路

### 思路一：💥描述清楚 — description 要像说明书

**问题**：description 写得太模糊，多个 Skill 都能匹配上。

```
❌ 模糊的 description：
  refund-skill: "处理退款相关问题"
  order-skill: "处理订单相关问题"
  complaint-skill: "处理投诉相关问题"

  用户说"我要退票" → 三个都能匹配 → 系统懵了
```

**解决**：description 要写清楚**能做什么、不能做什么、什么时候调用**。

```
✅ 清晰的 description：
  refund-skill: "用户明确要求退款或退票时调用。处理退票资格查询、退票流程引导、退款进度查询。
                 不处理：订单修改、投诉赔偿、票务咨询。"
  order-skill: "用户要查询订单状态、修改订单信息、查看订单详情时调用。
                不处理：退票退款、投诉、新订单创建。"
  complaint-skill: "用户表达不满、投诉、要求赔偿时调用。需要先道歉再解决问题。
                   不处理：正常退票、正常查询。"
```

**关键**：写清楚边界（"不处理什么"），比写清楚功能更重要。

**面试话术**：
> "description 要像说明书一样，不只写能做什么，还要写不能做什么、什么时候调用。写清楚边界比写清楚功能更重要，因为误命中通常是因为边界模糊。"

### 思路二：💥分类分层 — 先粗后细

**问题**：50 个 Skill 平铺，系统要一次从 50 个里选。

**解决**：先分类，再选具体 Skill。

```
第一层：分类（5 个大类）
  ├─ 售前类：ticket-booking, seat-selection, price-inquiry, ...
  ├─ 售中类：order-create, payment-guide, order-modify, ...
  ├─ 售后类：refund, complaint, compensation, ...
  ├─ 知识类：faq, policy, venue-info, ...
  └─ 闲聊类：greeting, small-talk, ...

第二层：选具体 Skill
  用户说"我要退票"
  → 第一层：匹配到"售后类"（从 50 个缩小到 10 个）
  → 第二层：在售后类里匹配到"refund skill"（从 10 个缩小到 1 个）
```

**本质**：把"50 选 1"拆成"5 选 1" + "10 选 1"，每次选择的难度降低。

**面试话术**：
> "分类分层的核心是降低每次选择的难度。把 50 个 Skill 平铺变成两层选择：先从 5 个大类里选 1 个，再从 10 个具体 Skill 里选 1 个。每次选择的候选数量少了，命中率自然提高。"

### 思路三：💥Router 路由 — 专用路由器

**问题**：让主 Agent 自己判断该用哪个 Skill，负担太重。

**解决**：建一个专门的 Router，只做路由决策，不做其他事。

```python
# Router 的职责：三件事
def router(user_input: str) -> str:
    """
    1. 用户想完成什么？（意图）
    2. 需要什么能力？（能力域）
    3. 哪个 Skill 最匹配？（具体 Skill）
    """
    intent = classify_intent(user_input)       # "我要退票" → "退款"
    domain = map_domain(intent)                # "退款" → "售后"
    skill = match_skill(domain, user_input)    # "售后" → "refund-skill"
    return skill
```

**关键**：Router 要有"不选 Skill"的选项。

```python
def router(user_input: str) -> str:
    # 先判断是否需要 Skill
    if is_general_chat(user_input):       # "你好"、"谢谢"
        return None                       # 不加载任何 Skill
    if is_simple_query(user_input):       # "今天天气怎么样"
        return None                       # 不需要 Skill

    # 再匹配具体 Skill
    return match_skill(user_input)
```

**为什么要"不选"的选项**：

```
用户说："你好"
❌ 强制选一个 Skill → 加载了"闲聊 skill" → 可能反而限制了 Agent 的自然表达
✅ 不选 Skill → Agent 用默认行为回答 → 更自然
```

**面试话术**：
> "建专用 Router 做路由，不让主 Agent 硬猜。Router 只做三件事：**判断用户意图、确定能力域、匹配具体 Skill**。关键是 Router 要有不选 Skill 的选项，否则系统非要选一个反而效果下降。"

### 思路四：💥正反例教学 — 边界靠例子讲清楚

**问题**：只靠规则描述，边界模糊，容易误命中。

**解决**：在 Skill 里加正反例，让 Agent 知道"什么该命中、什么不该命中"。

```markdown
# Skill: 退票处理

## 正例（应该命中这个 Skill）
- "我要退票" → 命中 ✅
- "怎么申请退款" → 命中 ✅
- "我的票能退吗" → 命中 ✅
- "退票后多久到账" → 命中 ✅

## 反例（不应该命中这个 Skill）
- "我想换一个座位" → 不命中，应该用 order-modify skill
- "票太贵了能便宜点吗" → 不命中，应该用 complaint skill
- "演出取消了怎么办" → 不命中，应该用 policy skill（不是退票，是演出取消政策）
- "帮我查一下我的订单" → 不命中，应该用 order-query skill
```

**为什么反例更重要**：

```
误命中通常不是因为"正例太少"，而是"边界不清楚"

用户说"演出取消了怎么办"
  → refund skill 的 description 里写了"退款"
  → 系统觉得"取消 → 退款"，命中了 refund skill
  → 但其实应该用 policy skill（演出取消的政策，不是退票流程）

加了反例："演出取消了怎么办 → 不命中，应该用 policy skill"
  → 系统知道了边界 → 不再误命中
```

**面试话术**：
> "正反例教学的核心是：误命中通常不是正例太少，而是边界不清楚。反例比正例更重要，因为反例划清了边界。在 Skill 里加反例，告诉系统什么情况不该命中，比加更多正例更有效。"

## 三、四个思路的关系

```
描述清楚 		→ 	解决"每个 Skill 写得准不准"的问题
分类分层 		→ 	解决"Skill 太多选不过来"的问题
Router 路由 	 →   解决"谁来做选择"的问题
正反例教学 	   →   解决"边界模糊导致误命中"的问题
```

**组合使用的完整流程**：

```
用户输入
  │
  ▼
Router 路由（专用路由器，不是主 Agent）
  │
  ├─ 不需要 Skill → 直接回答
  │
  ▼
第一层：分类（5 个大类选 1 个）             ← 分类分层
  │
  ▼
第二层：选具体 Skill（用 description 匹配） ← 描述清楚
  │
  ▼
检查正反例（确认是否误命中）                 ← 正反例教学
  │
  ▼
加载 Skill → Agent 执行
```
