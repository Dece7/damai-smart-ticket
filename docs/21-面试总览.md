## 一、💥30 秒电梯演讲💥

面试官问"介绍一下你的项目"时：

> **我做了一个智能票务助手，基于 LangChain + LangGraph 构建。核心有三块：一是 RAG 知识库问答，Markdown 标题感知切分 + Parent-Child 分块 + BM25/向量混合检索，来源命中率 100%；二是 Agent 智能模式，9 个工具自动调用，6 节点结构化多 Agent 编排（意图分类→路由→子 Agent→回答生成→兜底）；三是 MCP 协议集成，把工具封装为标准 MCP Server，第三方客户端即插即用。**

**要点：** 先说技术栈，再说三个核心能力（RAG + Agent + MCP），最后点一下深度优化。不要从 Phase 1 开始按时间线讲。

## 二、系统架构口述

面试官问"讲讲你的系统架构"时：

```
整体分四层：

1. 前端层：Vue 3 + Vite 工程化，SSE 接收流式返回
2. 接口层：FastAPI，四个入口
   - /api/chat（贴心助手 + 规则助手）
   - /api/agent（Agent 智能模式）
   - /api/agent/multi（多 Agent 协作）
   - /api/admin（管理统计）
   - /api/knowledge（知识库管理）
   - /api/mcp（MCP 工具信息）
3. 服务层：
   - ChatService：Function Calling 多轮工具调用
   - AgentService：LangGraph ReAct Agent 编排
   - MultiAgentService：6 节点结构化多 Agent 编排（intent_classifier/router/ticket_agent/knowledge_agent/answer_generator/fallback）
   - MemoryService：会话历史持久化
4. 基础设施：
   - ChromaDB 向量数据库 + BM25 索引（Reranker 已关闭，英文模型对中文反效果）
   - DashScope Embedding（阿里云向量化模型）
   - SQLite 存储对话和消息
   - Mimo 模型 API（对话 + 查询改写）
   - MCP Server（工具标准化暴露）
```

**口述技巧：** 边说边画（面试有白板的话），从上到下讲，不要从底层往上讲。

## 三、技术选型理由

面试官问"为什么用 X 不用 Y"时的回答：

| 问题 | 回答 |
|------|------|
| 为什么用 LangChain 不用 LlamaIndex？ | LangChain 生态更成熟，LangGraph 的 Agent 编排能力更强，社区资源更多 |
| 为什么用 LangGraph 不用纯 LangChain Agent？ | LangGraph 用状态图编排，支持复杂流程控制，比纯 Agent 更灵活 |
| 为什么用 ChromaDB 不用 Milvus？ | 项目规模小（15 份文档），ChromaDB 轻量够用，无需部署独立服务 |
| 为什么用 BM25 + 向量混合检索？ | 单一向量检索对关键词精确匹配弱，BM25 补充了这个短板 |
| Reranker 为什么关闭？ | 英文 Reranker 对中文内容反效果（100% → 81.8%），生产环境需换中文模型 |
| 为什么用 SQLite 不用 MySQL？ | 本地开发阶段，SQLite 零配置，部署时可无缝切换到 MySQL |
| 为什么用 FastAPI 不用 Flask？ | FastAPI 原生支持异步、SSE 流式返回、自动 API 文档 |
| 为什么用 Mimo 模型？ | 免费额度，OpenAI 兼容协议，支持 Function Calling |
| 为什么不用 DeepSeek Embedding？ | DeepSeek 不提供 Embedding API，用阿里云 DashScope 替代 |
| 为什么做多 Agent？ | 单 Agent 工具多时选择困难，多 Agent 各司其职决策更精准 |
| 为什么做 MCP？ | 不只会用 MCP，更能做 MCP，体现工程前瞻性 |

**回答原则：** 先说"为什么选它"，再说"它的局限是什么，什么场景下会换"。体现你不盲目，有判断力。

## 四、踩坑与解决

面试官问"遇到什么困难？怎么解决的？"时，挑 2-3 个讲：

### 坑 1：RAG 链拿不到 Token 用量

**问题：** RAG 链用了 `StrOutputParser`，它会丢弃 AIMessage 对象，导致 `usage_metadata` 丢失。

**尝试：** 先试了 `stream_usage=True`，发现无效；再试 `astream_events` 捕获 `on_chat_model_end`，但 `AddableDict` 报错。

**解决：** 改用 `llm.get_num_tokens()` 按输入/输出文本长度估算，虽然不如 API 返回精确，但对成本监控够用。

**学到：** Chain 的输出解析器会丢弃元数据，需要在解析前捕获；流式链的事件模型比直接读 chunk 复杂。

---

### 坑 2：Agent 工具内部 LLM 输出误推送

**问题：** Agent 模式下，工具内部调用的 LLM（如查询改写）的流式输出被推送到前端，导致回答中出现"退票政策和退款流程"等无关文字。

**原因：** `on_chat_model_stream` 事件处理器捕获了所有 LLM 流式事件，包括工具内部的。

**解决：** 加 `inside_tool` 标记，工具执行期间（`on_tool_start` → `on_tool_end`）的 LLM 流式事件不推送给前端。

**学到：** LangGraph 的 `astream_events` 会捕获所有子图的事件，需要过滤。

---

### 坑 3：多 Agent 路由消息干扰子 Agent（已重构解决）

**问题：** 早期架构用 `__route__:knowledge` 消息标记做路由，被传给子 Agent 导致工具调用错误。

**旧方案：** `_filter_route_messages()` 过滤路由标记消息。

**当前方案：** 重构为结构化 state 路由——`intent_classifier` 输出 `state.intent`，`router` 读取 `state.route` 决定去向，不再往消息体里塞标记。

**学到：** 路由决策应该用结构化字段，不要用消息体"暗号"。结构化 state 更可观测、可追踪、可恢复。

---

### 坑 4：英文 Reranker 对中文反效果

**问题：** 启用 Reranker 后来源命中率反而下降（100% → 81.8%）。

**原因：** 使用的 Reranker 模型 `ms-marco-TinyBERT-L-2-v2` 是英文模型，对中文内容排序不准确，把正确文档排出了 Top-5。

**解决：** 关闭 Reranker，默认不启用。生产环境换中文 Reranker（如 BGE-Reranker-v2-m3）。

**学到：** Reranker 模型的语言适配很重要，英文模型不能直接用于中文场景。

| 指标 | 数据 | 说明 |

| Embedding 模型 | DashScope tongyi-embedding-vision-plus | 阿里云多模态 Embedding，1024 维 |
| 来源命中率 @5 | 100% | DashScope Embedding + Parent-Child 分块（HashEmbedding 基线 23.6%，DashScope 基线 56.4%） |
| Precision@5 | 55.7% | Top-5 结果中相关文档占比 |
| MRR | 0.992 | 几乎全部排第 1 位 |
| 关键词命中率 | 98.5% | 65 条测试用例 |
| LLM Judge 综合 | 4.9/5 | 相关性 5.0，忠实度 5.0，完整性 4.7 |
| 单次对话 Token | 500-5000 | Agent 模式偏高（多轮工具调用） |
| RAG 检索延迟 | 320ms | BM25 + 向量混合检索，本地 ChromaDB |
| 流式首 Token | <1s | Mimo API 响应快 |
| 工具调用轮次 | 最多 5 轮 | 防止 Agent 死循环 |
| 测试用例数 | 65 条 | 离线评估体系（55 knowledge + 5 ticket + 5 both） |

- 知识库从 2 份扩充到 15 份，覆盖完整票务场景

- MCP 协议集成：9 个工具封装为 MCP Server，第三方客户端即插即用
- 前端工程化：Vue 3 + Vite + Element Plus + ECharts
