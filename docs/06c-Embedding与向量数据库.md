# Embedding 与向量数据库构建

> 向量数据库构建八步：
>
> 文档采集  →  文档解析  →  文本清洗  →  Chunking  →  Embedding  →  元数据绑定  →  写入向量数据库  →  构建索引

---

## 全景图

```
文档采集   →   文档解析   →   文本清洗   →  Chunking   →   Embedding   →   元数据绑定   →   写入向量库   →   构建索引
   ↓             ↓            ↓             ↓              ↓               ↓              ↓             ↓
.md/.pdf      提取文本       去噪去重       分块            向量化          绑定属性         ChromaDB       HNSW
.docx         结构化         格式标准化     重叠            维度选择        来源/分类        持久化          IVF/PQ
.html         表格/图片      语言检测       标题感知        模型选择         权限/版本        批量写入        参数调优
```

---

## 一、💥文档采集

### 做什么

把知识源的原始文档收集到统一的存储位置。

### 常见来源

| 来源 | 格式 | 处理方式 |
|------|------|---------|
| 本地文件 | .md, .txt, .pdf, .docx | 文件系统读取 |
| 数据库 | 结构化数据 | SQL 查询导出 |
| API 接口 | JSON, XML | 调用接口获取 |
| 网页爬虫 | HTML | 解析 DOM 提取文本 |
| 用户上传 | 任意格式 | 文件上传接口 |

### 本项目

本地 `docs/rag/*.md` 文件，12 个 Markdown 文档。

### 面试要点

- 文档采集要考虑**格式多样性**，不同格式需要不同的解析器
- 生产环境需要考虑**增量采集**，不是每次全量重新采集
- 数据源可能有**权限控制**，采集时需要记录权限信息

---

## 二、💥文档解析

### 做什么

把不同格式的原始文档统一解析为纯文本，保留结构信息。

### 常见解析器

| 格式 | 解析工具 | 注意点 |
|------|---------|--------|
| Markdown | `TextLoader` / 正则 | 保留标题层级（#/##/###） |
| PDF | `PyPDFLoader` / `pdfplumber` | 表格、图片提取困难 |
| Word | `Docx2txtLoader` | 格式丢失问题 |
| HTML | `BeautifulSoup` | 去除标签，保留文本 |
| Excel/CSV | `pandas` | 表格数据需要特殊处理 |

### 本项目

```python
loader = DirectoryLoader(
    str(doc_dir),
    glob="**/*.md",
    loader_cls=TextLoader,
    loader_kwargs={"encoding": "utf-8"},
)
```

### 面试要点

- 解析的核心挑战是**保留结构信息**（标题、列表、表格）
- PDF 解析最复杂，表格和图片需要 OCR 或多模态模型
- 解析后的文本需要**保留元数据**（文件名、路径、页码等）

## 三、💥文本清洗

### 做什么

去除噪音数据，标准化文本格式，提高后续 Embedding 质量。

### 常见清洗操作

| 操作 | 说明 | 示例 |
|------|------|------|
| 去除特殊字符 | 去掉 HTML 标签、控制字符 | `<br>` → 空 |
| 去重 | 删除重复段落 | 相同的 FAQ 答案 |
| 格式标准化 | 统一标点、空格、换行 | 全角/半角统一 |
| 语言检测 | 识别文档语言 | 中文/英文分开处理 |
| 长度过滤 | 过短的文本块丢弃 | < 10 字的碎片 |
| 敏感信息脱敏 | 手机号、身份证号 | 138****1234 |

### 本项目

当前没有显式的文本清洗步骤，Markdown 文档本身比较干净。

### 面试要点

- 清洗质量直接影响 Embedding 质量，垃圾进垃圾出
- 中文文本需要特别注意**全角/半角**、**繁简体**、**标点符号**标准化
- 去重很重要，重复内容会导致检索结果偏向重复文档

---

## 四、💥Chunking（文本切分）

### 做什么

把长文档切成合适大小的文本块，每个块作为一个检索单元。

### 切分策略

| 策略 | 说明 | 适用场景 |
|------|------|---------|
| 固定字符切分 | 按字符数切，不考虑语义 | 最简单，效果最差 |
| 递归字符切分 | 按分隔符递归切（段落→句子→词） | 通用场景 |
| 标题感知切分 | 按 Markdown 标题层级切 | 结构化文档 |
| 语义切分 | 按 embedding 相似度检测语义边界 | 长文档 |
| Parent-Child 切分 | 大块套小块，小块检索大块返回 | 需要精准+完整 |

### 关键参数

| 参数 | 作用 | 调参建议 |
|------|------|---------|
| `chunk_size` | 每块最大字符数 | 短文档 400-800，长文档 1000-1500 |
| `chunk_overlap` | 相邻块重叠字符数 | chunk_size 的 10%-20% |
| `separators` | 切分优先级 | 段落 > 句子 > 词 > 字符 |

### 切分质量的影响

```
切太大 → embedding 语义分散 → 检索不准
切太小 → 上下文断裂 → LLM 回答不完整
切在错误位置 → 知识点被截断 → 检索和生成都差
```

### 本项目

```python
# Markdown 标题感知切分 + Parent-Child
md_splitter = MarkdownHeaderTextSplitter(
    headers_to_split_on=[("#", "h1"), ("##", "h2"), ("###", "h3")],
)
child_splitter = RecursiveCharacterTextSplitter(
    chunk_size=400,      # Child 块
    chunk_overlap=80,
)
# Parent: 800/150, Child: 400/80
```

### 面试要点

- Chunking 是 RAG 效果的**第一道关**，切分不好后面都白搭
- Parent-Child 是当前主流方案：小块语义集中适合检索，大块上下文完整适合生成
- chunk_size 要根据文档特点调参，没有万能值
- 切分要尽量**尊重文档结构**（标题、段落、列表）

## 五、💥Embedding（向量化）

### 做什么

把文本块转换为高维向量，用于后续的向量相似度检索。

### Embedding 模型对比

| 模型 | 维度 | 特点 | 适用场景 |
|------|------|------|---------|
| HashEmbedding | 384 | 无语义，仅哈希映射 | Demo/测试 |
| OpenAI text-embedding-3 | 3072 | 通用能力强 | 英文为主 |
| DashScope tongyi-embedding-vision-plus | 1024 | 中文效果好，多模态 | 中文场景 ✅ |
| BGE-M3 | 1024 | 开源，中英文都强 | 本地部署 |
| Cohere Embed | 1024 | 多语言 | 多语言场景 |

### 模型选择要考虑的因素

| 因素 | 说明 |
|------|------|
| 语言 | 中文场景选中文模型，英文场景选英文模型 |
| 维度 | 不是越高越好，3072 维不一定比 1024 维好 |
| 延迟 | API 调用有网络延迟，本地模型更快 |
| 成本 | API 按 token 计费，本地模型免费但需要 GPU |
| 多模态 | 纯文本场景不需要多模态模型 |

### Embedding 的原理

```
文本: "退票政策"
  ↓ 模型编码
向量: [0.12, -0.34, 0.56, ..., 0.78]  (1024 维)
  ↓
存储到向量数据库，用于相似度计算
```

### 相似度计算

| 方法 | 公式 | 特点 |
|------|------|------|
| 余弦相似度 | `cos(A,B) = A·B / (|A|·|B|)` | 最常用，只看方向 |
| 欧氏距离 | `d = √Σ(Ai-Bi)²` | 看绝对距离 |
| 点积 | `A·B = ΣAi·Bi` | 向量已归一化时等价于余弦 |

### 本项目

```python
# HashEmbedding → DashScope tongyi-embedding-vision-plus
class DashScopeMultiModalEmbedding:
    def _call_api(self, texts):
        resp = dashscope.MultiModalEmbedding.call(
            model="tongyi-embedding-vision-plus",
            input=[{"text": text}],
            parameters={"dimension": 1024},
        )
```

### 面试要点

- Embedding 模型选择要**看场景**，不是越贵越好
- 维度不是越高越好，高维模型计算量大、存储成本高
- 同一个项目里 **Embedding 模型和检索模型要匹配**（用同一个模型 encode query 和 document）
- Embedding 模型应该是**可替换的**，通过配置切换，不改业务代码

## 六、💥元数据绑定（Metadata）

### 做什么

给每个 chunk 绑定业务属性，支撑过滤、溯源、权限控制等功能。

### 元数据分类

| 类别 | 字段 | 作用 |
|------|------|------|
| **来源信息** | `source`, `h1`, `h2` | 答案溯源 |
| **业务分类** | `category` | 按业务域过滤（票务/支付/场馆） |
| **文档类型** | `doc_type` | 按类型过滤（FAQ/政策/指南） |
| **时间信息** | `created_at`, `updated_at` | 版本管理、时效性 |
| **状态信息** | `is_active` | 过期文档过滤 |
| **权限信息** | `permission` | 权限控制（public/internal/vip） |
| **变更检测** | `doc_hash` | 增量更新 |
| **结构信息** | `parent_id` | Parent-Child 映射 |

### 元数据支撑的功能

| 功能 | 需要的元数据 | 说明 |
|------|------------|------|
| 答案溯源 | `source`, `h1`, `h2` | 回答标注来源 |
| 业务过滤 | `category` | 检索时只搜相关分类 |
| 版本管理 | `version`, `updated_at` | 文档更新历史 |
| 过期管理 | `is_active` | 标记过期文档不参与检索 |
| 权限控制 | `permission` | 不同用户看到不同文档 |
| 增量更新 | `doc_hash`, `updated_at` | 检测文档变更 |

### 本项目

当前只有 4 个字段：`source`, `h1`, `h2`, `parent_id`。

### 面试要点

- 元数据是**向量检索的第二维度**，向量管语义，元数据管过滤
- ChromaDB 支持 `where` 条件过滤，可以先过滤再检索
- 元数据设计要考虑**未来扩展性**，不要只存技术字段
- 权限过滤在企业级场景很重要，不能让用户看到无权访问的文档

## 七、💥写入向量数据库

### 做什么

把 embedding 向量和元数据持久化到向量数据库，支持高效相似度检索。

### 常见向量数据库

| 数据库 | 类型 | 特点 | 适用场景 |
|--------|------|------|---------|
| **ChromaDB** | 嵌入式 | 轻量、Python 原生 | 本项目 ✅，Demo/小规模 |
| **Milvus** | 分布式 | 高性能、可扩展 | 生产级大规模 |
| Pinecone | 云托管 | 免运维、按量付费 | 不想自建 |
| Weaviate | 自托管 | 支持多模态 | 多模态检索 |
| Qdrant | 自托管 | Rust 实现、高性能 | 高性能需求 |
| FAISS | 库 | Facebook 开源、纯内存 | 研究/小规模 |

### ChromaDB 基本操作

```python
import chromadb
from langchain_chroma import Chroma

# 创建持久化客户端
client = chromadb.PersistentClient(path="./chroma_db")

# 从文档构建向量库
vectorstore = Chroma.from_documents(
    documents=chunks,
    embedding=embedding_fn,
    client=client,
    collection_name="damai_rag",
)

# 相似度检索
results = vectorstore.similarity_search("退票", k=5)

# 带过滤的检索
results = vectorstore.similarity_search(
    "退票",
    k=5,
    filter={"category": "ticketing"}
)
```

### 写入方式

| 方式 | 说明 | 适用场景 |
|------|------|---------|
| 全量重建 | 删除旧数据，重新写入 | 文档变动少 |
| 增量更新 | 只更新变化的文档 | 文档频繁变动 |
| 批量写入 | 分批写入，避免内存溢出 | 文档量大 |

### 本项目

```python
# ChromaDB 持久化存储
client = chromadb.PersistentClient(path="./chroma_db")
vectorstore = Chroma.from_documents(
    documents=chunks,
    embedding=embedding_fn,
    client=client,
    collection_name="damai_rag",
)
```

### 面试要点

- 向量数据库选型要看**规模、性能、运维成本**
- ChromaDB 适合 Demo 和小规模，生产环境用 Milvus 或 Qdrant
- 写入时要考虑**增量更新**，不是每次都全量重建
- 向量数据库的**索引类型**（HNSW/IVF/PQ）影响检索速度和精度

## 八、💥构建索引（向量数据库不只是存数据）

### 为什么需要索引

向量数据库的核心价值不是"存"，而是"快速找"。

```
没有索引：暴力搜索（Flat）
  查询向量 vs 100 万个文档向量 → 逐一计算相似度 → 100 万次计算
  耗时：~1 秒

有索引：近似搜索（ANN）
  查询向量 → 通过索引快速定位候选集 → 只算 100 个 → 返回 Top-K
  耗时：~1 毫秒
```

**100 万次 → 100 次**，速度差 1 万倍。

### 常见索引类型

| 索引类型 | 原理 | 速度 | 精度 | 内存 | 适用场景 |
|---------|------|------|------|------|---------|
| **Flat（暴力）** | 逐一计算 | 慢 | 100% | 高 | 数据量小（<10 万） |
| **HNSW** | 多层跳表图 | 快 | 99%+ | 高 | 通用首选 ✅ |
| **IVF** | 聚类分区 | 中 | 95%+ | 中 | 数据量大 |
| **PQ（乘积量化）** | 向量压缩 | 快 | 90%+ | 低 | 内存受限 |
| **IVF+PQ** | 聚类+压缩 | 快 | 92%+ | 低 | 大规模+低内存 |

### HNSW 原理（最常用）

```
Layer 3:  A ──────────────── D          （粗粒度，快速定位区域）
Layer 2:  A ──── B ──── C ──── D        （中粒度）
Layer 1:  A - B - C - D - E - F - G - H （细粒度，精确查找）

查询：从顶层开始 → 逐层下降 → 每层找最近的邻居 → 最终定位到最相似的文档
```

类似 GPS 导航：先看全国地图定位到城市 → 再看城市地图定位到区 → 再看街道地图找到具体位置。

### 索引的关键参数

| 参数 | 作用 | 调参建议 |
|------|------|---------|
| `M` | 每个节点的连接数 | 16-64，越大越准越慢 |
| `ef_construction` | 建索引时的搜索宽度 | 100-200，越大索引质量越好 |
| `ef_search` | 查询时的搜索宽度 | 50-200，越大越准越慢 |
| `space` | 距离度量 | cosine / l2 / ip |

### 本项目

ChromaDB 默认使用 HNSW 索引，配置余弦相似度：

```python
client = chromadb.PersistentClient(path="./chroma_db")
collection = client.get_or_create_collection(
    name="damai_rag",
    metadata={"hnsw:space": "cosine"},  # 余弦相似度
)
```

### 面试要点

- 向量数据库不只是存数据，**索引才是核心**，决定检索速度和精度
- HNSW 是当前最主流的索引类型，速度和精度平衡最好
- 索引参数需要根据数据量和精度要求调优
- 数据量小（<10 万）用 Flat 就够了，不需要索引优化

## 本项目八步实现：当前 vs 完备链路

| 环节 | 完备链路（企业级） | 你项目 | 差距 |
|------|-------------------|--------|------|
| 文档采集 | API 上传 + 多格式支持 + 自动触发 | ✅ 有上传 API | 格式只支持 .md |
| 文档解析 | PDF/Word/HTML/表格 多格式解析 | ⚠️ 只有 TextLoader | 只支持纯文本 |
| 文本清洗 | 去重、去噪、格式标准化、敏感信息脱敏 | ❌ 没有 | 文档本身干净 |
| Chunking | 标题感知 + Parent-Child | ✅ 有 | 够用 |
| Embedding | 可切换模型、批量处理 | ✅ 有 | 够用 |
| 元数据绑定 | 来源/权限/版本/业务标签/过期时间 | ⚠️ 只有来源和标题 | 缺业务字段 |
| 写入向量库 | 增量更新、变更检测 | ❌ 全量重建 | 最大差距 |
| 构建索引 | HNSW 参数调优 | ✅ ChromaDB 默认 | 够用 |

**为什么当前没做完备链路**：15 个静态文档，全量重建 30 秒，增量更新的开发成本比它省下的时间还贵。生产环境文档量大时再补。

**面试话术**：
> "当前项目是 15 个静态文档，用全量重建够用。生产环境我会构建一套知识入库链路：文档上传后自动触发解析、清洗、切分、向量化，通过 Metadata 做权限和版本管理，支持增量更新。文档量小时全量重建，量大时用消息队列做异步处理。"

## 面试高频问题

| 问题 | 回答要点 |
|------|---------|
| 向量数据库构建有哪些步骤？ | 八步：采集→解析→清洗→切分→向量化→元数据绑定→写入→构建索引 |
| 向量数据库为什么要建索引？ | 不只是存数据，索引决定检索速度。暴力搜索 100 万次 vs HNSW 索引 100 次，差 1 万倍 |
| HNSW 索引原理？ | 多层跳表图，从顶层粗粒度定位逐层下降到细粒度精确查找，类似 GPS 导航 |
| Chunk size 怎么选？ | 根据文档特点：短问答 400-800，长文档 1000-1500，没有万能值 |
| Embedding 模型怎么选？ | 看语言（中/英）、维度、延迟、成本，不是越贵越好 |
| 为什么要加元数据？ | 支撑过滤、溯源、权限、版本管理，是向量检索的第二维度 |
| 全量重建 vs 增量更新？ | 小规模全量重建够用，大规模需要增量更新 |
| 向量数据库选型？ | Demo 用 ChromaDB，生产用 Milvus/Qdrant，不想自建用 Pinecone |
| Parent-Child 怎么实现？ | 小块做 embedding 检索，命中后映射回大块返回给 LLM |
| 怎么处理文档更新？ | 计算 doc_hash 对比，只处理变化的文档 |
