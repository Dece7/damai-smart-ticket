## 六、简历亮点逐条详解

### 1. LangGraph ReAct Agent + 9 个业务工具

**知识点：**

9 个工具分两类：

| 类型 | 工具 | 作用 |
|------|------|------|
| 查询类 | search_program、get_program_detail、get_ticket_info、query_ticket_status、check_order_status、calculate_price、get_recommendations、search_knowledge_base | 读数据，不修改 |
| 操作类 | create_order | 写数据，扣余票、生成订单 |

ReAct 是一个反馈循环机制：
```
思考（LLM）→ 调用工具 → 观察结果 → 再思考 → 再调用 → ... → 最终回答
```

LLM 是"大脑"，决定每一步做什么；工具是"手脚"，执行具体操作。用户说"帮我买两张680的票"，Agent 会依次调用 search_program → get_ticket_info → create_order，完成查票、查档、下单的完整流程。

**面试时怎么说：**
> "基于 LangGraph 构建 ReAct Agent，注册 9 个业务工具，分为查询类和操作类。Agent 自动判断用户意图选择工具，支持单次对话连续调用多个工具完成复杂任务。比如用户说'帮我买两张680的票'，Agent 会依次调用查节目、查票档、下单三个工具。"

### 2. RAG 多阶段检索架构

**知识点：**

这是项目的核心能力，完整流程：

```
用户问题: "怎么退票"
    │
    ▼
┌─────────────────────────────────────────────────────┐
│ 第1步：查询改写                                        │
│ "怎么退票" → "退票政策和退款流程"                        │
│ 用 LLM 将模糊问题改写为完整查询，~100ms                  │
└─────────────────────────────┬───────────────────────┘
                              │
                              ▼
┌─────────────────────────────────────────────────────┐
│ 第2步：粗排 — 两条路同时检索                            │
│                                                     │
│  路线A：BM25 关键词检索                                │
│    分词 → ["退票","政策","退款"...]                     │
│    在所有文档中找包含这些词最多的文档                      │
│    返回 Top-20 候选                                   │
│                                                     │
│  路线B：向量语义检索                                    │
│    Embedding → [0.12, -0.34, ...]                   │
│    在 ChromaDB 中找向量最相似的文档                      │
│    返回 Top-20 候选                                   │
└─────────────────────────────┬───────────────────────┘
                              │
                              ▼
┌─────────────────────────────────────────────────────┐
│ 第3步：RRF 融合排序                                    │
│                                                     │
│ 公式：score = weight / (60 + rank)                   │
│                                                     │
│ BM25 结果：                                          │
│   排名1: 节目取消和退票.md  → 0.9/(60+1) = 0.0148     │
│   排名2: 演出变更与延期.md  → 0.9/(60+2) = 0.0145     │
│                                                     │
│ 向量检索结果：                                        │
│   排名1: 演出变更与延期.md  → 0.1/(60+1) = 0.0016     │
│   排名2: 节目取消和退票.md  → 0.1/(60+2) = 0.0016     │
│                                                     │
│ 合并：同一文档分数相加                                 │
│   节目取消和退票.md = 0.0148 + 0.0016 = 0.0164 ← 最高 │
│   演出变更与延期.md = 0.0145 + 0.0016 = 0.0161        │
│                                                     │
│ 按总分排序，取 Top-20                                 │
└─────────────────────────────┬───────────────────────┘
                              │
                              ▼
┌─────────────────────────────────────────────────────┐
│ 第4步：Reranker 精排                                   │
│                                                     │
│ 粗排 Top-20 → Reranker 逐个打分 → 取 Top-5            │
│                                                     │
│ Reranker 是交叉编码器：                                │
│   粗排：query 和 doc 独立编码（双塔模型）               │
│   精排：query 和 doc 联合编码（交叉编码器）             │
│   联合编码能捕捉 token 级别交互，精度更高               │
│                                                     │
│ 实测：DashScope Embedding 下 Reranker 提升不明显      │
│ 因为 Embedding 本身已经足够精准                        │
└─────────────────────────────┬───────────────────────┘
                              │
                              ▼
┌─────────────────────────────────────────────────────┐
│ 第5步：组装 Prompt + LLM 生成                         │
│                                                     │
│ System: "你是规则助手，根据以下文档回答用户问题"         │
│ Context: [文档1] 来源：节目取消和退票                   │
│          退票需在演出详情页查看...                      │
│ User: "退票政策和退款流程"                             │
│                                                     │
│ LLM 基于文档内容生成回答，附带引用来源                   │
└─────────────────────────────┬───────────────────────┘
                              │
                              ▼
                    SSE 流式返回给前端
```

**关键概念解释：**

| 概念 | 是什么 | 解决什么问题 |
|------|--------|------------|
| BM25 | 基于词频的关键词检索 | 精确匹配（"退票"匹配"退票"） |
| 向量检索 | 基于 Embedding 的语义检索 | 语义理解（"怎么退"匹配"取消订单"） |
| RRF | 倒数排名融合算法 | 合并两种检索结果，不依赖原始分数尺度 |
| Reranker | 交叉编码器精排 | 对粗排结果二次排序，精度更高 |

**为什么需要多阶段：**
- 直接用 Reranker 精排所有文档太慢（131 个分块 × 逐个打分）
- 粗排（BM25 + 向量）快速筛出候选集
- 精排（Reranker）对候选集精确排序
- 平衡了速度和精度

**面试时怎么说：**
> "搭建 RAG 多阶段检索架构：BM25 + 向量粗排 → RRF 融合排序 → Reranker 精排。BM25 做关键词精确匹配，向量检索做语义理解，RRF 用倒数排名公式融合两种结果，Reranker 用交叉编码器精排。每条回答附带引用来源，用户可追溯到原始文档。"

### 3. 离线评估体系

**知识点：**

65 条标准问答对（55 knowledge + 5 ticket + 5 both），每条包含：
```json
{
  "question": "怎么退票？",
  "expected_sources": ["节目取消和退票-相关问题与回答"],
  "expected_keywords": ["退票", "退款"],
  "intent": "knowledge"
}
```

评估指标：
- Recall@5（召回率）：期望文档是否出现在 Top-5 结果中 → 100%
- Precision@5（精确率）：Top-5 中有多少是相关的 → 55.7%
- MRR（平均倒数排名）：第一个相关结果排在第几位 → 0.992
- 关键词命中率：检索结果是否包含期望关键词 → 98.5%
- LLM Judge：用 Mimo 对回答做相关性/忠实度/完整性评分 → 4.9/5
- 端到端延迟：从查询到返回的时间 → 320ms

支持 A/B 对比模式，量化每次优化的效果。

**面试时怎么说：**
> "建立 65 条标准问答对的离线评估体系，覆盖 knowledge、ticket、both 三种意图。评估维度包括检索质量（Recall@5=100%、Precision@5=55.7%、MRR=0.992）和生成质量（LLM Judge 4.9/5，无幻觉）。支持 A/B 对比模式，比如从 HashEmbedding（23.6%）到 DashScope Embedding（56.4%）再到 Parent-Child 分块（100%），每次优化都有数据支撑。"

### 4. 三模式对话架构

**知识点：**

| 对比维度 | Agent | 贴心助手 | 规则助手 |
|---------|-------|---------|---------|
| 技术实现 | LangGraph ReAct，自动判断意图选工具 | Function Calling，LLM 决定调工具 | RAG，固定先检索再生成 |
| 系统提示词 | SYSTEM_PROMPT_ASSISTANT | SYSTEM_PROMPT_ASSISTANT | SYSTEM_PROMPT_RAG |
| 对话历史 | ✅ 有 | ✅ 有 | ❌ 无（单轮） |
| 工具调用 | LLM 自动选择 9 个工具 | LLM 自动选择 9 个工具 | 固定调用知识库检索 |
| 推理步骤 | ✅ 展示工具选择过程 | ✅ 展示工具选择过程 | 只展示查询改写 |
| 知识库检索 | ✅（通过工具） | ✅（通过工具） | ✅（固定流程） |
| 适用场景 | 通用场景 | 查节目、下单 | 退票政策、规则问答 |

**核心区别：**
- Agent 和贴心助手功能相似，都是 LLM 自动选工具，区别在于 Agent 用 LangGraph 编排
- 规则助手是专用模式，固定走 RAG 检索流程，不调用其他业务工具
- 三个模式统一了知识库检索和来源展示，用户可根据场景选择

**面试时怎么说：**
> "设计三模式对话架构，Agent 模式用 LangGraph 自动选工具，贴心助手直接调业务工具，规则助手只检索知识库。三个模式统一了知识库检索和来源展示，用户可根据场景选择不同模式。"

### 5. Agent 推理过程可视化

**知识点：**

Agent 模式下展示推理过程时间线：
- reasoning（黄色）：LLM 决定调用哪个工具
- tool_start（蓝色）：开始执行工具
- tool_end（绿色）：工具返回结果

通过 LangGraph 的 `astream_events` API 捕获 Agent 内部事件，SSE 推送到前端，渲染为可折叠时间线。推理步骤持久化到数据库，切换对话时仍可查看。

**面试时怎么说：**
> "实现 Agent 推理过程可视化，将工具选择、执行、返回的完整链路以时间线形式展示。用 LangGraph 的 astream_events 捕获内部事件，SSE 推送到前端。推理步骤持久化存储，便于用户理解决策过程和开发阶段调试。"

### 7. Token 消耗统计 + 管理仪表盘

**知识点：**

三种模式的统计方式不同：

| 规则助手 | `llm.get_num_tokens()` 估算 |

管理仪表盘：总览卡片（总对话数、总消息数、总 Token）、每日趋势图（ECharts）、模式占比饼图。

### 9. 查询改写

**知识点：**

用户提问往往模糊、简短、口语化，直接检索效果差。查询改写在检索前调用一次 LLM，将模糊问题改写为完整查询：

```
"怎么退" → "退票政策和退款流程"
"那个周杰伦的" → "周杰伦演唱会门票信息"
"退票政策是什么" → "退票政策是什么"（已足够清晰，不改写）
```

用 Mimo 模型实现，~100ms 延迟。Prompt 中有规则"如果问题已经足够清晰，直接返回原问题"。

**面试时怎么说：**
> "实现查询改写功能，将用户模糊口语化提问自动改写为适合检索的完整查询。用 LLM 做改写，~100ms 延迟，原始问题足够清晰时不改写。提升 RAG 检索命中率。"

### 10. 多 Agent 协作（Supervisor 模式）

**知识点：**

Supervisor（监督者/编排者）是多 Agent 架构的一种模式：一个"总调度"负责分析任务，分派给专业子 Agent 执行。

三种多 Agent 模式对比：

| 模式 | 结构 | 特点 | 复杂度 |
|------|------|------|--------|
| **Supervisor** | 中心化，一个调度分派 | 简单、可控、易调试 | ★★☆☆☆ |
| **Hierarchical** | 树状层级，多级调度 | 适合复杂组织架构 | ★★★★☆ |
| **Swarm** | 去中心化，Agent 之间互相传递 | 灵活但难调试 | ★★★★★ |

项目选择 Supervisor 是因为最简单、够用。

工作流程：
```
用户: "帮我查演唱会，顺便告诉我退票政策"
    │
    ▼
Supervisor（LLM 分析意图）→ 输出 "ticket + knowledge"
    │
    ├→ 条件边路由 → 票务 Agent（8 个工具）
    └→ 条件边路由 → 知识 Agent（1 个工具）
    │
    ▼
各 Agent 独立执行，返回结果
```

关键点：
- Supervisor 本质是一个 LLM 调用，分析意图后输出路由字符串
- 条件边是路由机制，不是判断本身（判断是 LLM 做的）
- 子 Agent 各有独立的 system prompt 和工具集，决策更精准
- 子 Agent 之间不直接通信，通过共享状态传递

关键实现细节：结构化 state 路由（`state.intent` / `state.route`）、意图分类器流式输出过滤、answer_generator 单 Agent 透传优化、提示词约束不暴露内部标识。

**面试时怎么说：**
> "基于 LangGraph Supervisor 模式实现多 Agent 协作，编排 Agent 分析用户意图，将任务分派给票务专家或知识库专家。复杂问题自动拆解并行处理，各 Agent 有独立的 system prompt 和工具集，决策更精准。"

### 11. MCP 协议集成

**知识点：**

MCP（Model Context Protocol）是 Anthropic 提出的标准化协议，让 AI 模型以统一方式连接外部工具。

项目将 9 个工具封装为 MCP Server，其他 AI 客户端可以调用这些工具：

```
项目（MCP Server）              客户端（MCP Client）
┌──────────────────┐          ┌──────────────────┐
│ search_program   │◄─────────│ Claude Desktop   │
│ get_ticket_info  │◄─────────│ Cursor           │
│ create_order     │◄─────────│ 其他 AI 应用      │
│ ...共 9 个工具    │          │                  │
└──────────────────┘          └──────────────────┘
```

两种运行模式：

| 模式 | 启动方式 | 适用场景 |
|------|---------|---------|
| stdio | `python -m app.mcp.server` | 本地客户端（Claude Desktop、Cursor） |
| HTTP/SSE | `python app/mcp/server.py --http` | 远程客户端、Web 应用 |

部署方式：

| 方式 | 说明 | 适用场景 |
|------|------|---------|
| 本地运行 | 对方在自己电脑上运行 MCP Server | 开发/测试 |
| 远程部署 | 部署到服务器，通过 HTTP/SSE 连接 | 生产环境 |

**面试加分点：** 大部分候选人只会用 MCP（配置别人的 Server），你能做 MCP（自己写 Server），这是质的区别。

**面试时怎么说：**
> "将 9 个业务工具封装为 MCP Server，支持 stdio 和 HTTP/SSE 两种传输模式。第三方客户端（Claude Desktop、Cursor）配置 MCP Server 地址即可即插即用。我不只是会用 MCP，更能做 MCP，体现了对协议的深入理解和工程化能力。"
